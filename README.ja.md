# DLSS NR リバースエンジニアリング：AMD モジュール → クロス GPU ソース復元

> **一行でいうと**：AMD 側の DLSS NR モジュールに対する徹底的な静的リバースエンジニアリング研究 —— **再ビルド可能なソースツリーを復元する**ための土台であり、そこから**単一のクロス GPU コードベース**（ポータブル、Intel 加速、AMD 加速、NVIDIA 参照の各バックエンドを含む）を導くための研究です。研究は完了しており、どこで行き詰まったかも正直に示しています；**復元作業こそが次の段階です**。

## 🎯 このプロジェクトが向かう先（プロジェクト目標）

このリポジトリは静的解析として始まりました —— しかし解析は常に**目的のための手段**にすぎません。私たちが今、順を追って目指している目標は次のとおりです：

### Stage 1 —— ソースを復元する：メインプログラムを逆コンパイルする

*バイトを理解する*段階から**保守可能なソースツリー**へ移行します：メインプログラムを逆コンパイルし、読める・再ビルド可能なソースを復元します。カーネルパラメータ仕様（[`docs/04`](docs/04-Kernel-Parameter-Spec.md)）、重みコンテナ形式、および登録メカニズムは、忠実な再構築を**検証可能にする参照資料**です —— だからこそ、これらが最初に作られました。

> ⚠️ **既知のブロッカーを先に明示します。** *使える*ソースツリーを復元するには **`71 block → kernel` のディスパッチバインディング**が必要です；これがなければ、再構築されたスケジューリング層は真ん中に穴の空いたスタブのままです。そのバインディングは現在、**利用可能な条件下では入手できません**（4 つの経路すべてが閉ざされています —— [協力のお願い](#-協力のお願い埋められなかった-3-つのギャップ)と [`docs/06`](docs/06-Open-Gaps-and-Limits.md) を参照）。したがってこの逆コンパイル作業も**同じギャップに突き当たります**。それでもこの作業には価値があります —— ツリーの大部分は復元できます —— が、ディスパッチ層を逆コンパイルだけで閉じることはできません。

### Stage 2 —— どこでも動く共通命令セットのビルド

最適化の前に、まず**動くように**します。**ベンダー独自の命令セットを一切使わない**ビルド —— 素朴でポータブルな計算経路 —— を生成します。これにより正しさが確立し、後続のあらゆるバックエンドに**比較対象となる既知の良好な参照**が与えられます。

### Stage 3 —— ベンダー別の加速ビルド

ポータブルビルドが動作したら、**ベンダー固有の加速**を独立したバックエンドとして追加します：

| バックエンド | 対象 | 加速経路 |
|---|---|---|
| **Intel 加速** | Intel Arc (Xe) | Xe Matrix Extensions (XMX) |
| **AMD 加速** | AMD RDNA / CDNA | HIP と行列コア |
| **NVIDIA オリジナル** | NVIDIA | ベンダー自身の NGX / DLSS 実装 |

> ⚠️ **NVIDIA 経路に固有の制約。** 本リポジトリは **NVIDIA の著作権で保護されたバイナリを含みません**（[`LEGAL.md`](LEGAL.md) §8）。また、公開されている NVIDIA コンポーネントの複製は、**分析可能なカーネルメタデータを一切持たないインターフェース層**であると確認されています（[`EXTERNAL_BINARIES.md`](EXTERNAL_BINARIES.md) と [`docs/03`](docs/03-DLL-Structure-Analysis.md) を参照）。したがって NVIDIA 経路は、**インターフェースの挙動および結果の相互検証のための参照**として利用できます —— 逆コンパイル可能なカーネルの供給源では**ありません**。ここでの NVIDIA 側の作業はすべてインターフェース／ドキュメントの水準にとどまります。

### Stage 4 —— ひとつのコードベースで、すべての GPU

バックエンド選択の仕組みを備えた**単一のソースツリーへ各バックエンドを統合**し、**ひとつのコードベースがサポート対象のすべての GPU を対象とする**ようにします —— ポータブル経路は汎用のフォールバックとして、ベンダー加速はそれが利用できる場所で。

> **一文でいうと：** *ソースを復元する → ポータブルに動かす → ベンダーごとに加速する → ひとつのクロス GPU コードベースに統合する。*

> **これらのステージの現状。** Stage 2–4 は**意図された方向を示すものであり、完了した作業ではありません**。本リポジトリに現在含まれているのは**解析とツールのみ**です —— 逆コンパイルされたソースツリーも、バックエンド実装もありません。ここで公開されているものはすべて**静的なバイト水準**です。証拠を示せない進捗をほのめかすより、このことを率直に述べる方を選びます。

## 🙏 協力のお願い：埋められなかった 3 つのギャップ

これは**「完了した」研究ではありません**。静的に確定できることはすべて突き止めました —— **34 個のカーネル名、カーネルパラメータのレイアウト、重みコンテナの形式、194 件のインポート面はすべて確定済み**です —— しかし、原作者が利用できる条件下では**3 つのギャップ**がどうしても埋められません。ここで明確に協力を求めます。

### ギャップ 1：`71 block → kernel` の対応関係（**最重要**）

**必要なもの**：どの層（`blockN.layerM`）が 34 個のカーネルのどれを呼び出すのか。

**取得できない理由**（4 つの経路すべてが閉ざされており、それぞれに証拠があります）：
1. **DLL の静的解析は限界に達している** —— ディスパッチ関数の本体はカーネル起動関数とまったく交差しない。
2. **ワークスペース内のソースは空殻である** —— 再実装プロジェクトは存在するが、そのディスパッチ関数の本体は `return true;` のみであり、この DLL とは**非同型**である（34 個のカーネル名のうち一致するのは 2 個だけ）。
3. **重みファイルは調べ尽くした** —— **140 個のバイトパターン**で、**ペイロードを含むファイル全体**を検索した：`shape` / `dtype` / 演算子種別 / `block` インデックス / `kernel` 名はすべて**0 ヒット**であり、インデックス領域のバイト単位の帰属計算でも**未帰属バイト = 0**（第 2 のテーブルも、隠しメタデータ領域も存在しない）。
4. **実行時観測は利用できない** —— AMD ハードウェアを持っていない。

**提供していただけるもの**：① 上流のネットワーク定義（`.onnx` / `.safetensors` / エクスポートスクリプト）、② 上流の pass 側ソース、③ または AMD ハードウェア上で実行して実際のディスパッチ列をダンプしたもの —— Issue を立ててください。**これは移植ロードマップが実現できるかどうかを直接左右します。**

### ギャップ 2：2 つのパラメータ構造体の内部フィールドレイアウト

**`VarParams`（168 バイト、5 個の `k_swin_var` カーネルのユーザーパラメータ構造体）** と **`SwinParams`（40 バイト、`k_swin_1h_32_fp8`）** は、内部のフィールド構成が未解明です。

**判明していること**：DLL のメタデータは `by_value` パラメータの**総バイト数**（168 / 40）のみを宣言しており、**フィールド名もフィールド境界も持っていません**。再実装のソースツリーにある同名の構造体（64 ビットポインタと仮定して 92 バイト）も読んでみましたが、それらは **168 とも 40 とも一致しません** —— したがって、そのソース側の構造体は DLL 側のレイアウトとして**使えません**。

**提供していただけるもの**：上流ソースの構造体定義、または AMD ツールチェーンの `by_value` 構造体レイアウト規則（暗黙のパディングを含む）—— Issue を立ててください。

### ギャップ 3：Intel Xe / XMX 側の能力確認（**51 項目のチェックリスト**）

34 カーネル × 演算子のマッピング表を作成しましたが、**表の「XMX が直接サポートするか」と「推奨パス」の 2 列は、34/34 行すべてが「外部資料の確認が必要」と記されています —— 能力に関する結論は意図的に出していません**。Intel のツールチェーンも Xe ハードウェアも持っておらず、検証できないからです。

**Intel Arc / oneAPI / Level Zero / SPIR-V に詳しい方**は、具体的な項目の確認にご協力ください（最優先：行列積・畳み込みに対する XMX プリミティブのサポートと精度モード、split-K リダクションの順序が仕様で制約されるか、Swin のウィンドウ／シフト系プリミティブ、そして汎用 SPIR-V パスの実現可能性の境界）。チェックリストは [docs/05-Intel可行性评估.md](docs/05-Intel可行性评估.md) の第 8 章にあります。

> **本プロジェクトの方法論**：確信が持てないものはすべて「外部資料の確認が必要」と記し、**決して推測しません**。表にある空白は**意図的なものであり、抜けではありません**。

## このプロジェクトが行ったこと

AMD 側の `dlssnr_amd_pass1.dll`（HIP の `amdgcn` デバイスコードを含む `version.dll` プロキシモジュール）を完全に静的解析し、次の問いに答えることを目的としています：

> **DLSS NR を AMD HIP から Intel Arc（Xe / XMX）へ再コンパイル／移植できるか？**

### 主な成果（すべて再現可能）

| 成果 | 内容 | ドキュメント |
|---|---|---|
| **モジュール形態** | 12 セクション；17 個のエクスポートは**すべて `version.dll` の API 名**（各々 16 バイトの `FF 25` ジャンプスタブ）；インポート面は **194 件 / 10 DLL**、うち `amdhip64_7.dll` が **29** 件の HIP API を供給 | `docs/03` |

### 確定した結論（自らの訂正を含む）

私たちは**訂正の履歴を残しました**。過去の自分たちの結論を覆したものも含みます：

- ✅ **34/34 の登録ペアリングは直接のバイト証拠である**（かつては「消去法による推論」と書かれていた）。
- ✅ **重みの実測がソースコードの定数を覆した**：実際の層構成は **1×47 / 4×15 (23–29, 40–47) / 5×9 (30–38)** であり、ソースの「ボトルネックは一律 4 層」と矛盾する（**不一致ブロック: 10 = 30–39**）；衝突した場合は**データファイルが優先される**。
- ✅ **`descsz` の差分は 1,410 から 938 に訂正された**（算術ミス）。重複排除後は **6 個の異なる値**がある。
- ✅ **「上流ソースが存在しない」という制約は覆された**：ワークスペースには pass 側のソースツリーが**確かに存在する**（ただし DLL とは非同型）；以前の「存在しない」は検索範囲が狭すぎたことによる**偽陰性**だった。
- ✅ **`71 block` の列挙上限は未確定である**：この数値は文書への転記にのみ現れ、DLL 内に対応する即値は存在しない。

> 私たちの方法論における厳格な規則が一つあります：**いかなる「X は存在しない」という主張も、範囲 + パターン + ヒット数を提示しなければならない。** だからこそ、ドキュメントには再現可能な「0 ヒット」の記録が多数登場します —— これは意図的なものです。

## 3 つの環境制約（ご注意ください）

すべての結論はこの 3 つの制約に縛られており、ドキュメント内でも随所に明示しています：

1. **AMD ハードウェアがない** ⇒ 実行時観測ができない（3 つのギャップの中で最も重要なもの）。
2. **AMDGPU 逆アセンブラがない**（`llvm-objdump` が利用できない）⇒ デバイス側の逆アセンブルができず、`swin_layer` などのシンボルの呼び出し関係は未証明である。
3. **Intel ツールチェーン / Xe ハードウェアがない** ⇒ Xe / SPIR-V / XMX の具体的な能力に関する事柄はすべて**「外部資料の確認が必要」と記し、結論を出さない**。

**したがって本プロジェクトの結論の水準は「静的バイトレベル」です**：出せるものはバイト証拠とともに出し、出せないものは「未解決」と記して外部資料を求めます。
