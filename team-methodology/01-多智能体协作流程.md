# 多智能体协作流程

本研究由**多个专职智能体协作**完成，角色的职责边界被刻意设计为**互不重叠、互相取证**。本文记录该流程，因为它是本研究能在大量结论上取得可信度的重要原因。

## 1. 角色划分

| 角色 | 职责 | 关键约束 |
|---|---|---|
| **侦察** | 清点材料、建立现状基线、登记已确认约束 | 只登记，不做结论 |
| **逆向分析** | 从二进制/源码/数据文件中提取事实并给出结论 | 每条结论必须给出可回溯证据 |
| **独立验证** | 对他人结论**独立重算**，并于必要时给出更正 | **不得采信自报值**；可推翻结论 |
| **综合** | 汇总各方产出为单一交付物 | 冲突必须以裁决结果为准，不得把未定写成已确认 |
| **独立验收** | 对最终交付物做独立复核与抽样核查 | 判定只有 ACCEPT / needs_revision，不接受自辩 |

**关键设计**：验证与验收**不与产出方共享结论**，只共享**原始材料与判据要求**。这使错误无法通过内部共识存活。

## 2. 角色之间的分工原则

### 2.1 结论必须可被独立重算

要求产出方在结论中给出**足够让第三方重算的信息**，而不是"我算过了"。例如：给出坐标换算公式、给出的字节区间、给出命中数。

### 2.2 验证方必须自建解析链

独立验证方被明确要求**自写解析器**，而不是复用产出方的脚本或中间 JSON。这在本研究中多次产生价值 —— 因为**同一份错误脚本被复用会掩盖错误**。

### 2.3 允许并鼓励推翻

验证方被授权直接给出**与原结论相反的结论**，且要求同时给出「原结论 → 我的证据 → 更正后结论」。本研究中由此产生的更正包括：

- 界定了两类地址区间的差别（内存范围 vs 指针项范围）；
- 修正了一处字节事实（某个字段的统计口径）；
- 修正了一处算术错误（一个派生量的求和）；
- 推翻了一处「无上游源码」的高影响约束（源码确实存在，只是当时检索范围不足）；
- 修正了一处「文件不存在」的假否定。

### 2.4 上游错误必须传播自查

当某个数字/结论被更正后，要求**对该数字在交付物全文内的所有出现做传播检索**，并给出检索范围与命中数。理由是：**局部修正而未传播，会留下自相矛盾的文档**。

## 3. 消息与记忆

- **记忆不随协调者转移**：协调者与成员之间只有消息，而成员之间**不共享上下文**。因此所有跨角色信息都必须**落盘为文件**。
- **交接文件**：当协调者或团队换代时，写一份"冷启动交接文件"，包含：必读材料清单（含指纹）、已确认约束、已闭合项、未闭合项、任务定义、纪律。新成员只读该文件即可接手。
- **任务状态回写**：成员须在完成任务后回写任务状态；若工具报错导致无法回写，则由协调者接管收口（撤销旧尝试 → 记录结论）。

## 4. 失败处理

- **成员失败就唤醒同一成员，不换人**（保留其已落盘的中间产物）。
- **唤醒时缩小范围**：把原本较大的任务切成"一次只做一小节、写完立刻落盘"的节拍。这是本项目在部分模型上**唯一稳定可行**的推进方式。
- **崩溃不丢工作**：因为要求"每写完一节立刻落盘"，成员崩溃后已落盘内容保留。

## 5. 本流程的代价（如实记录）

- **重复劳动**：共用一个邮箱导致非收件人也会看到发给某成员的更正，若不标注"仅针对某人"，会产生多余核对。
- **换代会丢上下文**：归档重建团队后，成员的会话记忆丢失，必须依赖交接文件；且成员 ID 变化，指挥者需要重新解析成员身份。
- **需要额外的人工裁决**：当两个角色给出冲突结论时，必须有明确的"以什么为准"的判据层级，否则流程会僵持。
