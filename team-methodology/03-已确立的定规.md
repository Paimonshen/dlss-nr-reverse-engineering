# 已确立的定规

本文是一份**逆向分析研究过程中实际踩坑后立下的方法论规则**清单。

需要先说清楚一件事：**这些规则不是从教科书上抄下来的最佳实践，而是"每一条都对应一次真实事故"**。它们的共同来源是同一个模式 —— 某个结论已经被写进交付物、已经进入下游、已经开始被引用，然后有人发现在更宽的范围里它不成立。每一条规则的存在，都意味着**先发生过一次违反**：一次假否定、一次漂移的引用、一次漏项的计数、一次把自己修回原样的"更正"。

因此本文的读法不是"遵守规范"，而是"**别人已经替你付过学费，照着做可以少付一次**"。

## 关于本文与《质量门禁与验收链》的关系

《质量门禁与验收链》给出的是**门禁的结构与其持有的 12 条简明纪律**；本文是它的**展开版与证据版**：把同一批纪律按主题归类，并为每一条补上

- **规则陈述**（做什么）
- **具体事故**（当时到底错在哪，错值 vs 正确值）
- **合规做法**（下一次怎么落地）

两者不重复：那边是"有哪些门"，这边是"每条门规是怎么被撞出来的"。

## 主题一：证据与追溯

### 1.1 每条结论必须带五要素

**规则**：任何字节级结论必须同时给出 **VA / RVA / 文件偏移 / 原始字节 / 反汇编或解析文本** 五项；源码类结论用「文件路径 + 行号 + 原文片段」替代后两项。

**事故**：一份分析报告给出了"簇 #3 位于某地址"的结论，并列了 VA 与 file 两列。复核发现该行的 VA 比真值低 `0x400`，而它填在"file"列里的其实是**真正的 RVA**（`0xB06B`），文件偏移真值是 `0xA46B`。另一行则相反：file 值比真值**高** `0x400`。同一个报告里同时出现了两种相反方向的偏移错误，根因是**地址换算的基准从来没有被固定在契约里** —— 有人用 `VA − 映像基址`，有人用 `VA − 节 VA`。

**合规做法**：契约里写明基准公式（例如 `.text` 段 `file = VA − 节 VA + 节 RAW 基址`）；结论表同时给 VA、RVA、file offset 三个值，让三者的算术关系可以被读者当场验算。

### 1.2 全称否定必须给「范围 + 模式 + 命中数」

**规则**：凡断言"不存在 X"，必须同时给出①检索范围、②匹配模式、③命中数，并说明该范围是否覆盖全库。

**事故**：分析方在一次检索中报告某模式的命中数为 0，据此断言"不存在"。但那次检索只覆盖了一个子树，而目标其实位于工程根目录下。**一次范围不足的"不存在"就是一次假否定。**（本条另有专节展开，见「主题二」。）

**合规做法**：报告 0 命中时，把"我搜了什么、用什么模式、在哪些根目录下搜、排除了什么"一并写出。搜索范围为 0 的结论与搜索范围明确的结论，可信度完全不同。

### 1.3 区分「强结论」与「测量证据」

**规则**：不要把一次测量的产物当成一条已经确立的结论。

**事故**：团队为某张指针表登记了"被重定位表覆盖"的结论，随后被推翻 —— 首次测量漏掉了两个覆盖来源（一张表被 26 条、另一张被 5 条重定位条目覆盖）。定位类定语还发生过另一类失效：一个地址的**数值与字节**被三轮验收逐字节核对过，但**没有一个人核对过它在节表中的归属**，于是"该地址位于某函数体内"这个从未被字节验证过的定语，一路通过了三道门。

**合规做法**：**定位类定语必须与数值证据一样，单独落一条可复核判据**（例如"位于某段区间内"必须给区间的起止与包含关系），否则"已核"只覆盖了数值、未覆盖定语。测量产物要标注其为"本次测量值"，并在结论成立前补一次独立复现。

## 主题二：区间与边界

### 2.1 区间端点必须独立确定

**规则**：凡区间类判据，端点必须先独立确定，不得沿用先前假设的边界。

**事故**：本项目在同一原因上发生过**两次**事故：分析沿用了早先假定的分界值去切分数据，而该分界值本身从未被独立验证过，于是切出来的两侧统计都错了。

**合规做法**：切分数据之前，先把端点当作一个**独立的待证事实**去测量；端点的来源要写清是"实测"还是"沿用"。若沿用，必须标注"未独立复核"。

### 2.2 「X 不存在」需要第二次、更宽的检索

**规则**：凡"某文件/目录不存在"的断言，必须在**更宽的范围内二次检索**后才能成立。

**事故**：协调方在自己的检索范围内按扩展名递归列举，得到 0 命中，据此断言"`CMakeLists.txt` / 构建脚本 / `README.md` 不存在"，并**据此打回了一名成员的正确证据**。成员复核后发现：这些文件确实存在，只是在**项目根目录**下，而协调方只查了子目录。协调方因此撤回并致歉。这是**假否定直接造成误判成员产出**的一次实例。

**合规做法**：把检索范围与排除项写成结论文本的一部分；结论从"不存在"改为"在范围 R 内 0 命中"，并把 R 的定义一起给出。扩展一次范围（到父目录/工程根）后再下否定结论。

## 主题三：计数与穷尽性

### 3.1 「表内每行合格」≠「表的条数等于母集」

**规则**：**"逐项核"与"穷尽核"是两个独立动作，前者通过不蕴含后者。** 凡文档中出现"总表 / 全部 / 每条 / 均 / 穷举"等全称或穷尽性表述，必须同时做①逐项核（每行是否合格）与②穷尽核（表的条数是否等于母集大小），两者各需独立的可复算方法。

**事故**：本项目在同一型失效上留下了**三个互为印证的实例**：

- **文档侧**：一份交付文档的"里程碑可验证性总表"标题写"每条给可复算判据"，实际只列了 **14** 条，而全文实际有 **23** 个里程碑。标题的"每条"与正文某节的"**全部**里程碑均给出可复算判据"共同构成**不成立的全称断言**。
- **协调侧**：协调方首轮核对时**只验了"总表内每行是否给判据"**（14 行都有判据 → 判定通过），**未核对"总表条数 == 里程碑总数"**，因此完整错过了同一维度。
- **验收侧（自曝）**：验收方最初**按任务书给出的"14"直接开工**，差点只做"这 14 行是否给判据"、重犯同型错误；改用对文档全文的正则去重扫描后才得到 23。

**合规做法**：把两个动作写进同一个核验契约；穷尽核必须用**对全文的独立扫描**，不得直接采信上游给的数字 —— **上游/任务书给出的数字本身同样需要被独立复核**。

### 3.2 冲突项计数必须给「预测规则 + 逐项明细 + 冲突项总数」

**规则**：凡"冲突项计数"的表述，必须三者齐备：预测所依据的规则、逐项明细、冲突项总数。

**事故**：协调方报告源码规则与实测数据的冲突时，**只举例了"5 层块 30–38"共 9 个**，遗漏了另一个块。按预测规则逐项复算后，冲突项实际是 **10 个**：9 个块是"预测少 1 层"（预测 4 层 / 实测 5 层），另 1 个块是"**预测多 3 层**"（预测 4 层 / 实测 1 层）。后者的冲突性质**更严重** —— 它说明源码里"某区间 = 瓶颈层、其外 = 解码器"的分段规则本身也不成立，因为该块位于瓶颈区内却只有 1 层。**只举例而不给总数，就会漏掉性质更严重的那一项。**

**合规做法**：用一句可复算的预测规则（如"区间 `[a,b]` 内 N 层、其余 1 层"）覆盖全部条目，再逐项列出不一致条目并给出总数与净值分解。净差应能与两侧总数之差闭合（本例 `9×(+1) + (−3) = +6`）。

### 3.3 计数被更正后必须做全文传播自查

**规则**：一个计数被更正后，必须对**全文**做一次"范围 + 模式 + 命中数"的传播自查，找出所有引用过旧值的位置。

**事故**：一处计数被更正后，旧值仍残留在另一份下游文档里被继续引用，直到该文档被独立复核时才暴露。更宽地说，本项目把这类问题归纳为同一个母题：**"一处更新、多处须同步"的传播问题** —— 它与"基线漂移"同源（见主题五）。

**合规做法**：更正发生时，建立一份**传播清单**：列出所有引用该值的候选文件与位置，逐处确认已刷新或明确标注为历史引述。

## 主题四：数字与语义

### 4.1 同一个数字可以携带互不相关的语义

**规则**：凡"同一数字"在不同语义下重复出现，必须先做语义核实，**不得用子串计数判定对错**。

**事故**：协调方用 `count("145")` 统计某数字，发现它出现在一份下游文档里，于是要求作者"把 145 改成 146"。逐行核实后发现，该文档**从未包含那个错误**；它文件内该数字的两处出现都是**完全无关的语义**：

- 一处是某内核某项寄存器原始数据里"逐目标最大值 = 145"——**这是寄存器实测数据**；
- 另一处是另一内核代码尺寸 `14528` 的**子串**。

**若按该指令执行，会篡改这两处真实数据。**（指令当场撤回。）真正含该算术错误的其实是另一份报告，且已由其作者自曝更正：它把"两个不相邻区间共 45 个"算错了（`23 + 23 = 46`，不是 45），因而预测层总数写成了 145，**正确值是 146**，与实测值之差是 `+6` 而非 7。两个主语的错误性质完全不同。

**合规做法**：作任何数字级指令前，逐行打开**每一处命中**看上下文语义；子串计数只能用来**发现候选位置**，不能用来**判定对错**。跨文档的同一数字默认视为无关，除非两侧的语境都被读过。

### 4.2 绝不转述未经复核的数字

**规则**：向他人转述任何数字前，必须先独立复算；若无法复算，必须显式标注其为"**他方自报值、未复核**"。

**事故**：协调方在同一轮内**三次**因未复核转述而发出错误指令或误判：①基于范围不足的检索断言"某文件不存在"（见 2.2）；②向复核方直接转述一个未经复核的算术值；③把"层总数 145"当成了另一份文档的错误（见 4.1）。三次的共同机制是**把上游的二手值当成自己的结论再向下游发**。

**合规做法**：转述句强制带来源标签。二手值只能以"某方自报、未复核"的形式出现，且不得作为下游的判定依据。

### 4.3 「源码常量 vs 数据文件实测」冲突时以数据文件为准

**规则**：源码常量与数据文件的实测值冲突时，**以数据文件为准**。

**事故**：工程源码里有一个硬常量限制每块最大层数，另有一个按区间返回层数的函数；而**从数据文件独立解析出的层数分布与两者都不一致**，实测出现了源码规则不会产生的层数混排。源码是移植者的假设，数据文件是从原始产物里提取的**硬证据**。同一工程树内还发现**两个互斥的权重头魔数常量，且都与实测首字节不符**；与该实测逐字段一致的，反而是另一处测试/加载器实现。

**合规做法**：冲突时给**判据层级**：数据文件 > 源码常量；并在报告中列出全部候选常量与各自"能/不能与字节闭合"的判据。同一工程树内存在多个互斥常量时，**以"能与字节闭合"的那个为准**。

### 4.4 字段取值不得按单个条目归因

**规则**：字段取值不得按具名条目单点归属，除非该取值在完整条目口径下的出现次数为 1；否则一律给"**取值 + 出现次数**"。

**事故**：一处统计把某字段的取值按**具名条目**来写（"某内核 = 58,368、另一内核 = 28,928"），与同一文件另一处的口径互斥。按完整条目口径复算后，这些取值是**分布**（某取值出现 8 次、另一取值出现 16 次、再一取值出现 6 次……），并不是某个条目的专属属性。

**合规做法**：凡是"字段 × 取值"的表格，列为"取值 + 出现次数 + 口径（条目数）"；出现次数 > 1 的取值不允许挂到单个名字下。

### 4.5 归属类表述必须先核对全集

**规则**：凡"外部文件 vs 容器内节"的归属类表述，必须先逐节核对该容器的节名全集。

**事故**：一处结论把某个大体积数据登记为容器内的一个节。核对节名全集后发现，该容器**根本没有那个节**；该体积的数字属于另一个完全不同的二进制，而真正的数据实体是一个**外部文件**（首字节魔数与结论所指的格式一致）。若该错误未被拦截，下游的一个分析方向会按**错误的数据定位**开工。

**合规做法**：写"数据在 X 里"之前，先打印 X 的节名全集；体积数字与节名必须来自同一个对象。

## 主题五：基线与时序

### 5.1 下游文档落盘前必须重取上游哈希

**规则**：下游文档（综合 / 汇总 / 验收报告）落盘前，必须对全部上游输入文件**重取哈希**，不得沿用写作过程中早先采集的值。

**事故（基线漂移）**：一份汇总文档登记了若干上游输入的哈希。其中两份输入在该汇总文档落盘**之前**刚完成返修，另一份报告也在其后做了更正。**汇总方取的是返修前的基线，却在其后落盘。** 后果：登记的哈希中有 3 份失效 —— **内容零失真**，但基线不可复现。该问题由独立复算在验收阶段发现（判为高严重度）。

**合规做法**：把"重取上游哈希"列为下游文档的**落盘前强制步骤**，而不是写作开始时的一次性准备。

### 5.2 引用型文档必须同时记录采集时刻

**规则**：引用型文档必须同时记录三样：各输入的哈希、各输入的**采集时刻**、自身落盘时刻。若某输入的修改时间晚于采集时刻，该引用即为**漂移引用**，须重新采集后刷新。

**事故**：同上起事故。因为没有记录采集时刻，漂移无法在写作过程中自检发现，只能在事后由独立复算倒推出来。

**合规做法**：在输入表里增加"采集时刻"列，并在落盘前做一次机械比较：**任何输入的 mtime 晚于采集时刻 → 停下重采**。

### 5.3 「基准版本」≠「实测版本」

**规则**：**复验的第一步必须是"重新取指纹并核对其是否仍是被验的那一版"**，而不是直接沿契约携带的指纹开工。

**事故**：一份报告落盘后，协调方在**复验任务已派发之后**对该报告代改了 1 个词，文件从 221,032 B 变为 221,074 B、指纹随之改变，**而复验契约仍携带旧指纹**。所幸复验方以**实测为准**、如实报出新值，没有为满足契约而假定"文件未变"。**隐性风险**：若复验方只核契约指纹、不逐项复算，就会**漏掉这次改动并误判"文件未变"**。

**合规做法**：复验契约必须携带新指纹 + 最后写入时间；若要代改，必须在派发复验**之前**完成，或代改后**重新派发**。这与 3.1 同型 —— 都是"两个独立动作不可互相蕴含"：3.1 是"逐项合格 ⇏ 穷尽"，本条是"契约指纹相符 ⇏ 仍是被验版本"。

### 5.4 任何改动后必须重新取指纹复核

**规则**：任何改动（哪怕只改 1 个词）完成后，必须**重新取指纹并复核"目标性质是否达成"**，不得假定"我改对了"。

**事故**：协调方按验收意见把一个严重度档位词从高改低，**但在自己新增的留痕句里又写了那个高位的裸词**（"初稿标：高位"），于是**恰好重新制造了"全文该词仅剩 1 处"这一同型矛盾** —— 修 bug 的动作本身引入了同型 bug。复算指纹时才发现，把留痕句改成不含裸词的表述后，该词才真正归零。

**合规做法**：**"修一个矛盾"时必须同步检查"我的修正是否引入了同类矛盾"**，否则会在原地打转。落盘后立刻重取指纹并跑一遍产生该矛盾的同一检查。

### 5.5 上游返修后必须通知下游刷新基线

**规则**：上游返修完成后，必须**主动触发**已落盘的下游文档刷新基线。

**事故**：上游返修完成时，下游汇总文档的输入登记表已经落盘但尚未刷新（即 5.1 的事故）；当时没有任何机制把"上游变了"这件事推给下游，全靠事后独立复算发现。

**合规做法**：返修闭环的最后一步是**通知下游**，并把"已通知的下游清单"记入返修记录。

## 主题六：自指与指纹

### 6.1 自指涉哈希不能内载于文件自身

**规则**：**原始哈希不可内载于文件自身**（写入即改变该值）。文末载有自身哈希的文档，内载的只能是**规范化自指哈希**；而**对外引用一律以现场实测的原始哈希为准**。

**事故**：交付物普遍在文末放一个指纹块。若把原始哈希写进去，写入动作会立即让该值失效 —— 这是一个自我否证的写法。

**合规做法**：把指纹行替换为**定长占位**后再取 SHA256，得到"规范化自指哈希"用于自我一致性校验；报告与引用中使用**原始文件哈希**，并**说明口径**（是原始哈希还是规范化哈希）。

### 6.2 不要引用自报的字节数/行数

**规则**：不要引用文档末行"自报字节数 / 行数"这类自照值 —— 它未必与磁盘实际一致。

**事故**：一处台账按早先记录写某文件"154 行"，磁盘实测是 187 行。另有一次行数分歧是**口径差异**而非内容差异：一个统计把按分隔符切分产生的尾部空段计入了行数（312 vs 313），而 LF 计数、逐行读取计数都是 312。两种情形都说明自报值不可直接采信。

**合规做法**：字节数/行数一律以**磁盘现场实测**（并写明统计口径）为准；引用他处记录时标注其为二手。

### 6.3 同一格式存在多个互斥常量时，以能与字节闭合的为准

（本条亦见 4.3；放在此处是因为它是"指纹与自证"问题的一个实例。）

**事故**：同一工程树内，两处实现为同一权重格式定义了**互斥的魔数常量**，且**两者都与实测首字节不符**；第三处实现（测试用权重分析器）与实测**逐字段一致**。另有注释自称某常量等于某个 ASCII 串，而该常量的小端字节实际拼出的是**另一个串** —— **注释与常量自相矛盾**。

**合规做法**：以能与字节闭合的实现为准，并在报告中列出**全部候选 + 各自的命中/失败判据**；不要采信注释的自述。

## 主题七：消息与协作

### 7.1 定向消息必须显式标明收件范围

**规则**：发给单一成员的更正/指令，若需其他成员忽略，**必须在消息开头显式写明**"本消息仅针对 X；其他成员无需回应或动作"。

**事故**：团队共用一个邮箱。一条本意只针对某一名成员的更正，被其他成员读到后引发了**不必要的逐条自查**，重复消耗了大量工作。

**合规做法**：定向消息首行写清收件范围；非收件人看到后**不必逐条自查**，若确认该消息命中的是自己的产物，只需一行"该对象不是我的产物 + 我文件无需改动"。

### 7.2 归因句必须逐句标明主语

**规则**：凡涉及"谁的文件含/不含某错误"的表述，必须**逐句标明主语**；两个主语不同的事实不得并置。

**事故**：协调方把"某份文档含甲错误"与"另一份文档含乙错误"两件事并置转述，读起来像是同一份文档的问题。实际上一份文档**从未包含**被指控的错误（见 4.1），而另一份是**作者主动自曝**并已就地更正的。并置会**抹掉成员自曝更正的价值与轨迹**。

**合规做法**：分主语文书；每条事实各自带主语；对"自曝更正"必须保留其更正轨迹（原值、更正后值、更正位置）。

### 7.3 崩溃后唤醒同一成员并缩小范围

**规则**：成员崩溃后**唤醒同一成员，不换人**；唤醒时**缩小范围**、**每段写完立刻落盘**、**干净收尾**。

**事故**：曾有两名成员在极小任务（仅文件哈希复算 + 读文末指纹块）上**连续两次崩溃、零落盘**，整段工作没有留下任何可复用的中间产物。后续处置改为：唤醒同一成员、把任务切成更小的段、每段完成即落盘。

**合规做法**：把"分段 + 即时落盘"作为默认工作方式；崩溃恢复的成本取决于上一段是否已落盘。

### 7.4 每段写完立即落盘

**规则**：不要等到全部完成才落盘；每完成一段就立即写盘。

**事故**：同上。零落盘的崩溃意味着**全部中间推理与已验证片段一起丢失**，只能从头再来；而当时任务本身只有"复算哈希 + 读指纹块"这么小。

**合规做法**：把"段落级落盘"写进任务契约；崩溃恢复时以最后落盘的段落为起点。

### 7.5 成员自证改动范围的方法

**规则**：成员的"本次改动范围"自证，应当用**可复算**的方式给出，例如"回退本次改动 + 删除新增块后做零上下文 unified diff"。

**事故**：在只有口头声明"我只改了这几处"的情况下，改动范围无法被独立复算，于是"是否越界"只能靠信任。

**合规做法**：自证方式必须是**任何人都能重跑**的操作序列，而不是叙述。

### 7.6 验证者必须自曝工具缺陷并保留首轮错误输出

**规则**：验证者须**自曝工具缺陷**并**保留首轮的错误输出**。

**事故**：本项目的可信度在很大程度上来自成员的自曝：一处自曝曝出了**解析越界**的成因（未用头部声明的条目数作循环上界，导致解析器冲进载荷区，扫出 301 条而非 153 条）；另一处自曝曝出了指令集误用（先按 x86 相对调用指令扫描失败，改用目标平台的调用指令后仍无结果），自曝方**保留并公开了不可用的原始输出**。

**合规做法**：把"保留首轮错误输出"当作证据要求的一部分 —— 它是证明"这一次的结论不是重复上一次的错误"的唯一材料。自曝不视为失分，而视为**可信度来源**。

## 主题八：解析与边界（附加）

### 8.1 列表解析必须以头部声明的条目数为循环上界

**规则**：结构化载荷的列表解析**必须以头部声明的 count 作为循环上界**，不得"读到看起来不像为止"。

**事故**：协调方首轮解析一度**越界**：未使用头部的 count 上界，解析器冲进条目之后的载荷区，得出**完全错误的结果**。独立复核用"不设上界"的对照扫描反推出同一失控点（首次失控处落在载荷区、条目名字长度为 0），**独立复现了该错误成因**。

**合规做法**：解析器必须显式使用 count 上界，并在解析后用恒等式闭合校验（例如"条目区长度 + 载荷区长度 == 文件长度、差 0"）。

### 8.2 未初始化区间的"初值"必须先核对节边界

**规则**：谈未初始化区间的"初值"之前，必须先核对该节的 `SizeOfRawData` 边界。

**事故**：某节的 `SizeOfRawData` 远小于其 `VirtualSize` —— 也就是说，该节在文件里**根本没有映像数据**。若不做这个核对，就会把"文件里读到 0"误读成"初值为 0"。

**合规做法**：任何"某全局初值为 X"的表述，先确认该全局落在有文件映像的区间内；否则改写为"文件无初值、由运行期写入"，并给出写入者证据。

### 8.3 计数必须走指令边界，而不是字节匹配

**规则**：指令级计数（调用点数等）必须**按指令边界反汇编**得到，字节模式匹配只能作为**交叉校验**，且差异去向必须给出。

**事故**：曾出现同一对象的计数在不同方法下不一致（字节匹配数与指令边界解析数不同），若只报其中一个，读者无法判断哪个是对的，也无法判断差集去哪了。

**合规做法**：同时给出"按指令边界解析数 + 同区间字节模式命中数 + 差集去向"三项。

### 8.4 「关键锚点」类跨域对应必须两侧都给命中数

**规则**：凡"A 与 B 属同一命名体系、构成关键锚点"这类跨域对应表述，**必须两侧都给出命中数**。

**事故**：协调方只在**一侧**（某个符号表）看到两个名字，就宣称它们同时出现在另一侧源码命名体系里、构成关键锚点。成员对另一侧全树检索后发现**各 0 命中** —— 二者**只存在于一侧**。只看一侧就宣称对应，是错的。

**合规做法**：两侧各给"范围 + 模式 + 命中数"；任一侧为 0 命中时，该"锚点"表述即撤回。

## 结语：没有这些规则的代价

诚实地讲：**本文每一条规则，都是用一次真实的错误换来的。**

- "不存在"的假否定，代价是**误判了成员的正确产出**，并让一条高影响约束错误成立了很久；
- 基线漂移，代价是一份已落盘的汇总文档里 3 份哈希失效，**内容没错，但整条引用链不可复现**；
- 逐项核与穷尽核混淆，代价是一句"全部里程碑均给出判据"的**全称断言不成立**，而且它同时骗过了产出方和协调方的两轮自检；
- 只举几个例子而不给冲突总数，代价是**漏掉了性质更严重的那一项**，并让一条"分段规则成立"的错觉多活了一段时间；
- 用子串计数下数字指令，代价是**差点篡改两处真实数据**；
- 修矛盾时引入同类矛盾，代价是**原地打转一整轮**；
- 崩溃零落盘，代价是极小任务也要**从头再来**。

这些代价单看都不大 —— 没有一个导致研究结论整体崩塌。这正是它们容易被忽略的原因：**它们的形态永远是"内容零失真，但可信度受损"**。而一项以"结论可信"为首要目标的逆向研究，受损的恰恰是唯一不能受损的东西。

所以本文的建议只有一句：**在下一个项目里，不要重新发明这些规则 —— 直接沿用，把学费省下来。**
