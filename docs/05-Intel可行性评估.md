# Intel 可行性评估

**评估对象**：把 DLSS NR 从 AMD HIP（`amdgcn-amdgpu` 体系）重编到**所有带 XMX 引擎的 Intel 显卡** —— 既包括 Xe-HPG 代（**Arc A 系列**，Alchemist），也包括 Xe2 代（**Arc B 系列**，Battlemage），以及后续带 XMX 的代次。

**开发与验证机**：**Intel Arc B580**（Xe2 / Battlemage）。它是目前唯一物理可用的部件，因此是能够实测、编译与验证的那一块。**不得把它的能力推广到整个家族。** 凡本文档给出的、随代际变化的硬件能力，**可移植基线一律取"所有目标代际共同支持"的集合**；超出该集合的部分只能作为**运行期探测之后的可选快速路径**，不得作为假设。代际数据来源见 [`07-External-Evidence-Xe-Capabilities.md`](07-External-Evidence-Xe-Capabilities.md)。

**评估纪律**：凡涉及 Intel Xe / SPIR-V / XMX 的**具体能力**，一律标注「需外部资料」并给出待查方向，**不给结论**。凡属运行期、指令级、编译级的判断，一律标注为需外部条件。

### 2.3 `wavefront_size` 32 / 64 的影响

#### (a) 事实

| 目标 | triple | `wavefront_size` 分布（34 内核） |
|---|---|---|
| 1–7 | gfx10-3-generic / gfx11-generic / gfx1100 / gfx1101 / gfx1102 / gfx1200 / gfx1201 | `{32: 34}` 各目标 |
| 8 | gfx9-generic | `{64: 34}` |

- 272 条目口径频次：**32 × 238**（= 7 × 34）、**64 × 34**（= 1 × 34）；
- **不单点归属**：32 与 64 都是**整个目标维度**的取值 ⇒ 该字段的差异**完全落在目标轴上**，在内核轴上无差异；
- 原始字节证据：bundle `#1` 的 k0 值字节 = `20`（positive fixint = 32）；bundle `#8` 的 k0 值字节 = `40`（= 64）。

#### (b) 影响分析（**凡涉 Xe 具体数值处一律不给结论**）

| # | 分析项 | 内容 | 标注 |
|---|---|---|---|
| C1 | 该字段的语义 | `wavefront_size` 是 **AMD 的波前（wavefront）宽度** | 已证 |
| C2 | 维度不同 | Intel Xe 的 SIMD 宽度表述为 **SIMD8 / SIMD16 / SIMD32** —— 该表述来自**外部知识**，工作区内无字节判据；据该表述，它与 AMD 的 32/64 **不是同一维度**；重编时**须按 Xe 目标宽度重算「工作项 → 线程」的映射**，**不得沿用 32 或 64** | 需外部资料 |
| C3 | 32 vs 64 的目标轴差异 | 32 只出现在 `#1`–`#7`；64 只出现在 `#8 gfx9-generic` ⇒ `#8` 与 `#1`–`#7` 在结构参数之外还有一处系统性差异 | 已证 |
| C4 | 与 XMX 的关系 | **本工作区内无任何判据**能把 AMD 的 `wavefront_size` 映射到 XMX 的执行模型。XMX 的执行单位与 sub-group 相关，但**该相关性在本工作区内不可证**（自研工程树内 `sub_group` **0 命中**） | 未解 |
| C5 | 现有自研实现现状 | 现有 SYCL 代码用 `item<1>` 标量核，**未使用** `nd_item` / `sub_group`；其 GEMM 部分用 `joint_matrix`，但**未声明 sub-group 大小** | 已证 |
| C6 | **需外部资料（不给结论）** | Xe 上 **sub-group 大小的取值范围与如何显式指定**、**XMX 的执行模型**（DPAS 指令形态、所需 sub-group 宽度、tile 尺寸约束）、以及「XMX 是否要求特定 sub-group 宽度」 | 需外部资料 |
| C7 | **待查方向** | 见 §8 G-05 | — |
| C8 | 移植纪律 | 由于 C2 已明确「不得沿用 32 或 64」，**任何把 `wavefront_size` 直接当作 Xe SIMD 宽度的写法都不成立**；该字段在 Xe 侧应视为**仅用于记录 AMD 原值**，不参与 Xe 执行参数推导 | 已证 |
| C9 | 风险 | `#8 gfx9-generic` 的 64 是**孤立取值**（272 中 34 条），若统一策略错误地以 `#8` 为基准，会把 34 条全带偏 | 已证 |

### 5.1 权重实体与容器定义（**已完整解出**）

| 项 | 值 |
|---|---|
| 路径 | 外部权重文件 `dlssnr_on_amd_weights.bin` |

#### (a) 容器结构（逐字节确定）

```
偏移 0x00   8 字节   char[8]  magic = "DLSSNRW1"
偏移 0x08   4 字节   uint32   = 153        ← 条目计数
偏移 0x0C   4 字节   uint32   = 5,673      ← 索引区总长（含头部 16 B）
偏移 0x10   可变长   条目 × 153
偏移 0x1629         载荷区起点
```

**条目结构（可变长，按文件顺序排列）**：

```
uint8    nameLen          ← 条目名长度（实测取值域 {19, 20, 26}）
char[]   name[nameLen]    ← ASCII 条目名
uint64   offset           ← LE，相对「载荷区起点」的字节偏移
uint64   size             ← LE，该条目的载荷字节数
```

#### (b) 三条恒等式（**闭合到 0**）

| # | 恒等式 | 实测 |
|---|---|---|
| ① | 逐条走完终点 == `uint32@0x0C` | **5,673 == 5,673**，差 0 |
| ② | `Σ size` == 文件大小 − 载荷起点 | **147,683,778 == 147,689,451 − 5,673**，差 0 |
| ③ | `offset[0] == 0` 且 offset 链违例 | **`offset[0] = 0`；153/153 严格递增、`offset[i] == Σsize[0..i-1]`；链违例 0/153** |

**索引区逐字节记账**：`0x00`–`0x08` 魔数 8 B；`0x08`–`0x0C` 头字段 1（4 B）；`0x0C`–`0x10` 头字段 2（4 B）；`0x10`–`0x1629` **条目区 5,657 B**（= 153 × nameLen 字段 153 + name 字符串 3,056 + offset 字段 1,224 + size 字段 1,224）；`0x1629`–`0x8CD8FEB` **载荷区 147,683,778 B**。

**剩余未记账字节 = 0** —— 即在「条目 × 153 之外」**不存在**任何未被解释的字节，因而在索引区内**不存在**第二张表 / 附加字段区 / 填充区。

**无上界扫描反证（解析纪律的直接产物）**：若不以 header `count = 153` 作循环上界，无上界扫描得 **301 条**，**首次失控点 = file `0x5E15`、nameLen `0x00`** ⇒ 印证「**必须以 header 的 `count` 作为循环上界**」这一解析纪律。

### 5.2 权重头冲突的裁决

| 来源 | 位置与原文 | 常量 | LE 字节 / ASCII | 与实测相等 |
|---|---|---|---|---|
| 树内 `Engine.cpp` | `uint32_t magic; // 'DLNR' = 0x524E4C44` + 同名检查 | `0x524E4C44` | `44 4C 4E 52` / `DLNR` | **否** |
| 树内 `IntelEngine.cpp` | `uint32_t magic; // 'DLNR' = 0x524E4844` + 同名检查 | `0x524E4844` | `44 48 4E 52` / **`DHNR`** | **否** |
| 树内 `weight_analyzer.cpp` | `char magic[8]; // "DLSSNRW1"` + 校验 | `"DLSSNRW1"` | `44 4C 53 53 4E 52 57 31` | **是** |
| 树内 `InferenceEngine.cpp` | `strncmp(header_.magic, "DLSSNRW1", 8) != 0` | `"DLSSNRW1"` | 同上 | **是** |

**裁定**：**以 `DLSSNRW1`（8 B）为准**；`Engine.cpp` 与 `IntelEngine.cpp` 的 4 字节常量**均不对应实测文件中的任何字段**，**二者同错**，不存在「二选一」的空间。

**五条判据**：

| # | 判据 |
|---|---|
| N-1 | **冲突轴错位**：两个 32 位常量与实测**根本不在同一比较平面** —— 实测魔数是 **8 字节 char 数组**；两个 32 位常量是**单 `uint32_t` 字段**。用 32 位常量匹配 8 字节魔数，**构造上不存在相等情形** |
| N-2 | **两条恒等式闭合到 0**：以 `char magic[8]` + `numTensors@8` + `numBlockLayers@12` 解析，名称表终点 == 5,673、数据区 == Σsize、offset 链 0 异常 ⇒ **8 字节魔数布局被字节闭合验证**；32 位魔数布局**无法闭合** |
| N-3 | **`Engine.cpp` 自述其为重构推测**：注释原文「Reconstructed from decompiled weight loading code」 ⇒ 属**未对撞的推测结构** |
| N-4 | **`IntelEngine.cpp` 的常量与其自身注释不一致**：注释写 `'DLNR' = 0x524E4844`，但该常量的 LE ASCII 是 **`DHNR`** ⇒ 该定义内部自证有误 |
| N-5 | **两个常量互斥且都无法与文件闭合**：二者相差 `0x400`；且实测 `uint32@0 = 0x53534C44` 与**二者皆不等** |

**一处表述校正**：`5,673` 是 `uint32@0x0C` 的值，**未在 `weight_analyzer.cpp` 内硬编码**（字面串 `5673` / `0x1629` 命中 **0 处**），由运行时 `tellg()` 得到。
