### 1.1 各节的观察

- **`.hip_fat`** 是最大节（`SizeOfRawData` `0x657600` = 6,649,344 字节），承载 GPU 侧 fatbin 容器。其内部结构见 `02-分析方法论.md` §3。
- **`.pdata`** 的 `VirtualSize` `0x36B4` 与 **1,167 条** `RUNTIME_FUNCTION` 一致（`0x36B4 = 1167 × 12`），因此 `.pdata` 可作为**函数边界的闭集** —— 这是本项目大量分析的基准。
- **`.text`** 代码量 `0x54C36` = **347,190 字节**，是所有间接调用扫描的分母。
- **本节表不含 `.rsrc`** —— 该 DLL 无资源节。（147 MB 量级的实体是外部权重文件，与 `.hip_fat` 的 6,649,000 字节分开计量。）
- `.fptable` / `.hipFatB` / `.retard` 是体积很小（`0x18`–`0x100`）的辅助节。
- `.retarc`（`0x21F0`）承载 527 条 `DIR64` 重定位（见 §5.4）。

### 1.2 `.data` 文件映像边界（一处关键事实）

| 项 | 值 |
|---|---|
| `.data` VA | `0x180074000` |
| `VirtualSize` | `0x4390` |
| `PointerToRawData` | `0x72400` |
| `SizeOfRawData` | `0x2200` |

**文件映像只覆盖 VA `0x180074000..0x180076200`**；VA ≥ `0x180076200` 的部分**没有文件映像，加载时按 0 初始化（BSS 型）**。

因此 `0x180076390` / `0x180076394` / `0x180076398` / `0x180077394` / `0x180077398` **均无文件初值**。

**反证「按文件偏移读到的字节实属 `.pdata`」**：对 `0x180076394` 用 `file = VA − 0x180074000 + 0x72400` 会得到 file `0x74794`，而该偏移落在 `.pdata` 节（RAW `0x74600..0x77E00`）内 —— file `0x74794` = `.pdata` 节内偏移 `0x194` → 记录序号 **33**（0-based）、字段 `UnwindInfoRVA` = `0x6D2A8`；file `0x74798` → 记录序号 **34**、字段 `BeginRVA` = `0x2D20`。

⇒ 对 BSS 型全局「按文件偏移读到的字节」是**别的结构**，不构成该全局的初值。

### 2.3 代理机制的正确表述

> **17 个导出「名」是 VERSION.dll 的 API 名；导出「入口」是经 `.data` 段 17 项指针表（VA `0x180076440`）的 `FF 25` thunk。**

三点必须同时给出，否则会产生错误理解：

1. **导出表静态转发器 = 0** —— 这**不是** PE 转发器（Forwarder）机制。转发器机制要求 `AddressOfFunctions[i]` 落在导出目录**内部**，实测 17/17 落在 `.text`。
2. **导出入口是纯 stub** —— 每项 16 字节，6 字节 `FF 25` + 10 字节 NOP，无任何实际代码。
3. **跳转目标是 `.data` 的 17 项指针表，且该表未在 `.reloc` 中被覆盖、无文件字节** —— 即该表的填充发生在**运行期**，填充路径未取得证据（见 §7.2 U-6）。

**一处被反复误标的地址**：`0x180001AE0` **不是任何导出的函数体**。

- 导出 `VerQueryValueW` = **`0x180001AD0`**（16 字节 stub，字节 `FF 25 EA 49 07 00 66 2E 0F 1F 84 00 00 00 00 00`）；
- 导出 `VerQueryValueA` = **`0x180001AC0`**（纯 thunk）；
- `0x180001AE0` 是一个**独立的 `.pdata` 函数**（区间 `0x180001AE0..0x180001B6A`，长度 `0x8A` = 138），其内部两处调用必须**自 `0x180001AE0` 起算**：
  - `+0x4F`（VA `0x180001B2F`）：`E8 FC 3D 05 00` → `0x180055930`（`__hipPopCallConfiguration`）
  - `+0x7A`（VA `0x180001B5A`）：`E8 11 3F 05 00` → `0x180055A70`（`hipLaunchKernel`）

早期材料把同一段代码记在导出 `VerQueryValueW`（`0x180001AD0`）名下，**错误基址相差 `0x10`**。

## 4. `hipLaunchKernel` thunk 阶梯与调用机制

### 4.1 机制总览

`.text` 内的 HIP API 调用**全部经 `FF 25 disp32`（`jmp qword ptr [rip+disp32]`）thunk** 完成：

```
调用点  ──E8 rel32──>  thunk (FF 25 disp32)  ──>  IAT 槽  ──>  amdhip64_7.dll
```

thunk 区形态为 **16 字节步长**：`FF 25 …`（6 字节）+ `CC`×10 或 NOP 填充。

## 5. 两张 8 字节步长函数指针表

这是本 DLL 结构分析中最核心、也最容易出错的部分。

### 5.1 表项语义与槽位宽度（两项定案）

**定案一：表项语义 = 8 字节绝对 VA**（不是节内偏移 / RVA）。三条独立判据：

| # | 判据 | 结果 |

## 7. 遗留问题：`71 block` 的枚举语义

### 7.1 问题的形态

网络结构的拓扑常量在**工作区源码**中有定义（`NUM_BLOCKS = 71`、`ENCODER_END = 22`、`BOTTLENECK_START = 23`、`BOTTLENECK_END = 47`、`DECODER_START = 48`），权重文件的条目名也覆盖 `block0` … `block70` 共 **71 个 block、无缺号**。

但这些常量**只定义拓扑**，不定义「某个 block 调用哪一个内核」。

### 7.2 block 重编号语义（已定案）

`.text` 内存在**同签名**（`cmp r32, 0x1A`，编码 `83 F8 1A` / `83 F9 1A` / `83 FA 1A`）的比较，共 **6** 处。其中 **4 处为 block 重编号内联副本**：

| # | VA | RVA | file | reg | 所属 `.pdata`（idx / Start–End / len） | 映射结果写入 |
|---|---|---|---|---|---|---|

| 2 | `0x18000CD9D` | `0xCD9D` | `0xC19D` | eax | 117 / `0x18000CC30–0x18000D022` / 1010 | `mov [rsp+0xB8], eax`（`0x18000CDD0`） |
