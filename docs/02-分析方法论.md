# 分析方法论

本项目在**无 AMD 硬件、无 AMDGPU 反汇编器、无 Intel 编译工具链**的三重约束下（见 `01-项目背景.md` §2.2），全部结论都建立在**静态字节分析**之上。这决定了方法论的核心命题不是「用什么工具」，而是：

> **在只能读字节的条件下，如何使一条结论尽可能难以出错。**

本章给出的是一套可复现的方法与其配套的纪律。

---

## 1. 总原则

### 1.1 字节是最终判据

任何文档陈述、任何源码注释、任何既有摘要，都**不是**结论的依据。唯一可接受的依据是：

1. 目标文件的**原始字节**（给出文件 / VA / RVA 三重坐标，并附原始字节串）；
2. **PE / ELF 结构字段**（由字节按规范解析得到）；
3. **可复算的算术**（计数、恒等式、频次分布）。

相互冲突的陈述之间，一律以字节裁定。

### 1.2 坐标必须给到可回溯

每条关键结论都给出三重坐标，使读者能够独立复算：

| 坐标 | 含义 | 换算 |
|---|---|---|
| **file** | 文件偏移 | 按各节 `PointerToRawData` 与 VA 换算 |
| **RVA** | 相对虚拟地址 | `RVA = VA − 0x180000000` |
| **VA** | 虚拟地址 | 按 ImageBase 加 RVA 得到 |

本节用到的换算关系（均经实测校验）：

- `.text`：`file = VA − 0x180001000 + 0x400`
- `.rdata`：`file = VA − 0x180056000 + 0x55200`
- `.hip_fat`：`file = VA − 0x18007F000 + 0x78200`

校验点：VA `0x180012380` → file `0x11780`；VA `0x180055A70` → file `0x54E70`。

### 1.3 否证与证实同等重要

本项目记录的不只是「发现了什么」，还包括**「在什么范围内检索、命中多少」**。所有「不存在 X」的结论都必须给出三要素：

> **范围 + 匹配模式 + 命中数**

三要素缺一，该结论就不可复核。典型样例如「全文件检索 `softmax` / `silu` / `gelu` / `layernorm` / `matmul` / `gemm` / `wmma` / `mfma` / `dpas` / `xmx` / `subgroup` / `reduce`，命中各 0」。

## 2. PE 结构解析

### 2.1 解析方式

不依赖外部 PE 库，而是按 PE 规范手工解析 `DataDirectory` 各项。理由：本项目需要解析的字段（导出转发器是否存在、导入描述符逐条、`.reloc` 块结构、`LoadConfig` 目录）在三方库中往往被高层 API 抽象掉，而它们恰好是结论的判据。

### 2.2 解析项

| 项 | 位置 | 用途 |
|---|---|---|
| DOS / NT 头 | `0x00` / `0x80` | 定位 PE32+ 头与 OptionalHeader |
| `DllCharacteristics` | `OptionalHeader + 0x46`（file `0xD6`） | 判定 `DYNAMIC_BASE` / `HIGH_ENTROPY_VA` / `NX_COMPAT` / `GUARD_CF` 是否置位 |
| 节表 | `IMAGE_FILE_HEADER.NumberOfSections` | 12 节逐字段（RVA / VirtualSize / PointerToRawData / SizeOfRawData） |
| `DataDirectory[0]` 导出 | RVA 由目录给出 | `NumberOfFunctions` / `NumberOfNames` / `Base`、AddressOfFunctions、Forwarder 字段 |
| `DataDirectory[1]` 导入 | RVA `0x6B3F4` / Size `0xDC` | 逐描述符解 ILT / IAT 并读名字与 hint |
| `DataDirectory[5]` 重定位 | RVA `0x6DD000` / Size `0x1090` | 逐块解条目、类型分布、按节统计覆盖 |
| `LoadConfig` | 由 `DataDirectory[10]` 引出 | `GuardCFCheckFunctionPointer` / `GuardCFFunctionTable` / `GuardCFFunctionCount` |
| TLS 目录 | `DataDirectory[9]` | `AddressOfCallbacks` |

### 2.3 关键纪律：区分「有效端点」与「内存范围上界」

本节方法中最容易出错的一点，是把「某段区域的内存范围上界」当作「该结构的有效项末端」。

具体样例：两张函数指针表在早期材料中被记为 `表 A = 0x180056170–0x1800562C0`、`表 B = 0x180058A48–0x180058B90`。这两个端点是**内存范围**（该区间内的全部字节），**不是指针项范围**。8 字节步长下真正承载函数指针的槽位为：

- **表 A = 项 0–40**（`0x180056170`–`0x1800562B8`），其中项 0–25 / 30–32 为函数指针，项 26 / 33 / 41 为 NULL，项 27–29 为哨兵区，项 34–40 为辅助数据；
- **表 B = 项 0–4**（`0x180058A48`–`0x180058A68`），其后为负值哨兵。

**教训**：区间端点必须独立确定，不得沿用先前假设的边界。该纪律在一次重算中直接产生了数值差异 —— 同一检索用**窄口径**（表 A 槽 0–25 窗口 ∪ 表 B 槽 0–4 窗口）得 **97** 处，用**宽口径**（表 A 全表窗口 ∪ 表 B 窗口）得 **110** 处；差额 13 处全部来自被窄口径截掉的合法引用。两个数字都对，但必须写明取自哪一个口径。

## 3. `__CLANG_OFFLOAD_BUNDLE__` 拆包

### 3.1 容器形态

`.hip_fat` 节（VA `0x18007F000` / RVA `0x7F000` / RAW `0x78200`）以魔数 `__CLANG_OFFLOAD_BUNDLE__` 开头（**全文件唯一**）。

### 3.2 头部解析

按以下顺序解析：

```
对齐填充至 8 字节边界
uint64  numBundles
重复 numBundles 次：
    uint64  tripleSize
    char    triple[tripleSize]
    uint64  offset          ← 相对「数据区起点」的偏移
    uint64  size
```

`numBundles` 的原始 8 字节为 `09 00 00 00 00 00 00 00` = 9。

### 3.3 解析结果与边界校验

9 条条目中，1 条为 host 占位（**size = 0**）、8 条为 device bundle。边界校验项：

| 校验 | 结果 |
|---|---|
| 9 条 triple 串的实测字符数与声明 `tripleSize` | **9/9 一致** |
| triple 串内是否含 NUL 终止符 | 不含 |
| 末 triple 末字节位置 | 节首 + `0x229` |
| 8 字节对齐上界 | 节首 + `0x230` |
| 节首 + `0x230` 至节首 + `0x1000` | **3,536 字节全零填充** |
| 数据区真起点 | 节首 + `0x1000`（file `0x79200` / VA `0x180080000`） |

### 3.4 `#0` host 占位的三个后果

1. **不得对空区间做 ELF 解析** —— 空区间 `[0x79200, 0x79200)` 的解析会读到 `#1` 的字节，产生伪结论；
2. `.hip_fat` 内实际 device code object 数为 **8**（不是 9）；
3. **host 侧代码不在本 DLL 内** —— 该 bundle 未承载 host 目标文件。

### 3.5 `.hip_fat` 字节账目恒等式

用于交叉校验解析是否正确：

```
0x1000（头部与填充区）
+ Σ(8 条实体 size) = 0x6514F0
+ Σ(7 处间隙)      = 0x4FB8
= 0x6574A8  （= 节 VirtualSize）
```

8 条 size 逐项：

```
0x89728 + 0x11E0A0 + 0x11C068 + 0x11C068
+ 0x11E0A0 + 0x67B88 + 0x67B88 + 0x844A8  = 0x6514F0
```

差额 `0x5FB8` = 间隙 `0x4FB8` + 头部区 `0x1000`。该式成立的前提是 `#0` 计 0 字节。

## 4. device ELF 提取与解析

### 4.1 定位

每个 device bundle 在 `offset` 处的字节即一个完整的 ELF 文件，区间为 `[数据区起点 + offset, 数据区起点 + offset + size)`。

### 4.2 解析项

| 项 | 用途 |
|---|---|
| `e_ident` | 校验 `EI_OSABI`（`0x40` = ELFOSABI_AMDGPU_HSA）与 `EI_ABIVERSION`（`4`） |
| `e_machine` | 校验 `0xE0`（224 = EM_AMDGPU） |
| 程序头 / 节表 | 定位 `.text` / `.rodata` / `.note` / `.symtab` / `.strtab` / `.dynsym` |
| 节表闭合校验 | `e_shoff + e_shnum × e_shentsize == size` |

实测：8 个 ELF 的 `e_type = 0x3`、`e_machine = 0xE0`、`e_ehsize = 64`、`e_phentsize = 56`、`e_phnum = 9`、`e_shentsize = 64`、`e_shnum = 16`、`e_shstrndx = 14`，**8/8 相同**；`e_shoff + e_shnum × e_shentsize == size` 差 0；`e_machine = 0xE0` **8/8 命中**。

### 4.3 `.kd` 描述符

device ELF 的 `.rodata` 内有一组 kernel 描述符（`.kd`），每个 64 字节，按 `slot` 索引：

```
.kd 起点 = .rodata 内偏移 0xA180 + 64 × slot
```

字段布局（按字节实测）：

| 相对偏移 | 字段 | 宽度 |
|---|---|---|
| `+0x00` | `group_segment_fixed_size` | u32 |
| `+0x04` | `private_segment_fixed_size` | u32 |

`.kd` 的作用是**独立第二来源**：它承载的 LDS / 私有段需求可与 msgpack 元数据对撞。实测对撞结果：**272/272 一致**（三字段各 272/272），且 `entry == 代码符号 VA − .kd 符号 VA` **272/272、反例 0**。

样例：k1 的 `.kd` 在 `#1` @ `0xA1C0`，`group_segment_fixed_size` 字段读得 **64,640**；k7 在 `#8` 的 `private_segment_fixed_size` 读得 **404**。两者与 msgpack 侧逐值相符。

### 4.4 符号表

`.symtab` / `.strtab` / `.dynsym` 用于：

- 恢复内核的 C++ 修饰名（mangled name）；
- 读取代码符号的 `st_value` / `st_size`（用于 `codesz` 列）；
- 检出**不在 34 个内核名之内**的额外符号。

额外符号的检出样例：`_Z10swin_layerR7SwinLDSPKhRK10BlobLayouti`（**非模板**）仅存在于 `#2`–`#5` 四个目标，`#1` / `#6` / `#7` / `#8` 命中 0；`.symtab` 条目数 `#2`–`#5` = 348，其余 = 347，`#1` 与 `#2` 的符号集合差集恰为该符号一个元素；8 个 bundle 的符号并集 = 348、共有 = 347。

## 5. md-snapshot `.note` 节与 AMDGPU msgpack 元数据解码

这是本项目**最核心的元数据来源**。

### 5.1 `.note` 节定位

每个 device ELF 内有一个 `.note` 节，`sh_type = 7`（SHT_NOTE），`sh_flags = 2`。节内承载一条 note：

```
namesz  @ note + 0x00   （u32）
descsz  @ note + 0x04   （u32）
type    @ note + 0x08   （u32）
name    @ note + 0x0C
desc    @ note + 0x0C + align4(namesz)
```

实测（bundle `#1` 为例，`sh_name = 1`、`sh_addr = sh_offset = 0x238`、`sh_size = 0x8B88`）：`type = 32` = `NT_AMDGPU_METADATA`；name 为 ASCII `AMDGPU`（`namesz = 8`，含 NUL）。

**msgpack 文档起点** = `0x238 + 12 + 8 = 0x24C`（相对 bundle 起点）。

### 5.2 文档结构

msgpack 文档的顶层是一个 map，键为点号前缀的字段名：

```
{
  ".args": [ { ... }, ... ],          ← 参数数组
  ".name": "...",                     ← 内核修饰名
  ".symbol": "...",
  ".kernarg_segment_size": ...,
  ".kernarg_segment_align": ...,
  ".group_segment_fixed_size": ...,
  ".private_segment_fixed_size": ...,
  ".sgpr_count": ...,
  ".sgpr_spill_count": ...,
  ".vgpr_count": ...,
  ".vgpr_spill_count": ...,
  ".wavefront_size": ...,
  ".max_flat_workgroup_size": ...,
  ".workgroup_processor_mode": ...,
  ".uniform_work_group_size": ...,
  ".uses_dynamic_stack": ...,
  ".language": ...,
  ".language_version": ...,
  ...
}
```

### 5.3 参数条目

`.args` 是参数 map 的数组。键集合实测两种：

| 键集合 | 出现次数 |
|---|---|
| `{.offset, .size, .value_kind}` | **3,496** |
| `{.address_space, .offset, .size, .value_kind}` | **24** |

即全库 3,520 个参数中，**仅这 24 个** `global_buffer` 参数含 `.address_space`，实测值为字符串 `"global"`，原始字节 `A6 67 6C 6F 62 61 6C`。

**纪律**：`.value_kind` **不是内核级字段**，仅出现在参数 map 内（3,520 个参数各 1 个；内核 map 无此键）。早期材料中作为「设备入队符号」的键，在 8 目标 × 34 内核全库检索**命中 0**，该字段在元数据中不存在，不得按实际字段使用。

### 5.4 msgpack 编码宽度纪律（一处必须遵守的更正）

msgpack 的整数有多种编码宽度，**同一个数值可能有不同的编码字节**。项目中发现并更正过一处编码宽度误记：

| 项 | 值 |
|---|---|
| 字段 | `k_reproject` 的 `.kernarg_segment_size` |
| 数值 | **384** |
| 正确编码 | **`CD 01 80`**（`CD` = **uint16**，大端 `0x0180` = 384） |
| 坐标 | blob `#1` `[28169, 28172)` → file `0x80255` / VA `0x180087055` |
| 对撞 | `CD 01 80` 在 blob `#1` 命中 **1**、整 DLL 命中 **9**；而按 uint32 记法（`CE` + 4 字节大端）构成的编码串在 blob `#1` 与整 DLL **均 0 命中** |

**结论**：给出编码字节时，必须与解码后的数值同时校验 —— 用错误的编码宽度去检索，会得到「0 命中」的假否证。

编码对照（本项目涉及的常见值）：

| 数值 | 编码 |
|---|---|
| 12 | `0C`（positive fixint） |
| 24 | `18`（positive fixint） |
| 32 | `20`（positive fixint） |
| 40 | `28`（positive fixint） |
| 64 | `40`（positive fixint） |
| 80 | `50`（positive fixint） |
| 128 | `CC 80`（uint8） |
| 168 | `CC A8`（uint8） |
| 384 | `CD 01 80`（uint16） |

### 5.5 跨目标解码的一致性与差异性

8 个目标的元数据**并非等长**：3 个 device 目标的 `descsz` 最大最小差 **938**（`0x3AA`，`#1` `0x8B72` vs `#8` `0x87DA`）。因此：

> **跨目标一致性必须逐项做，不得假定 8 目标元数据逐字节相同。**

逐项做的结果（见 `04-内核参数规格.md` §3、§4）：

- **参数面**：`.kernarg_segment_size`、`.args` 元素数、逐参数 `.offset` / `.size` / `.value_kind` —— 238/238 判定格一致，`.args` 数组字节级 SHA256 相同 272/272（不同字节串种数 12），差异条目 0；
- **资源面**：16 个字段实体中，**8 个一致、8 个不一致**。

### 5.6 定位器回读校验

解析器本身也要被校验。做法：用独立的 msgpack 参考实现，对**全部 4,080 个区间**逐区间回读比对，**失败 0**。

## 6. 字节模式扫描

由于无 AMDGPU 反汇编器，host 侧 `.text` 的分析大量依赖**字节模式扫描**。这是一种快于反汇编约两个数量级、但只能回答「某模式出现在哪里」的方法。

### 6.1 扫描分母

`.text` 代码量 `0x54C36` = **347,190 字节**。所有「全 `.text`」类结论以该值为分母。

### 6.2 快路径：原始字节计数

直接对全节做模式匹配，**不按指令边界过滤**。这给出的是模式出现数的**上界**。

样例（全 `.text`）：

| 模式 | 含义 | 原始命中数 |
|---|---|---|
| `FF 15` | `call [rip+disp32]` | 407 |
| `FF 25` | `jmp [rip+disp32]` | 101 |
| `FF D0` | `call rax` | 28 |
| `FF D1` | `call rcx` | 1 |
| `FF D2` | `call rdx` | 6 |
| `FF D3` | `call rbx` | 5 |
| `FF E0` | `jmp rax` | 10 |
| `FF E1` | `jmp rcx` | 13 |
| `FF E2` | `jmp rdx` | 2 |
| `FF E3` | `jmp rbx` | 12 |
| `FF 24 25` | `jmp [disp32]` | 0 |

### 6.3 慢路径：按指令边界确认

原始字节计数是**上界**，必须再做一次按指令边界的确认，才能得到「真正的调用点」数。

样例（`FF 25` 计数 **101** 的分解）：

| 成分 | 数量 | 说明 |
|---|---|---|
| 导出 stub | **17** | `0x1800019D0`–`0x180001AD0`，步长 `0x10` |
| thunk 阶梯 | **55** | `0x1800558D0`–`0x180055C30`，步长 `0x10`，连续性校验通过 |
| 其余散落 | **29** | 逐地址清单列出 |
| **合计** | **101** | ✅ |

**纪律**：凡写「全 `.text` 有多少个调用点」，必须写明是**原始字节计数**还是**按指令边界确认后**的计数。两者可以相等（如 `E8` → `0x180055A70` 的 60 处，两种口径同为 60），也可以不等（如 dispatcher 函数体内 `E8` 原始命中 **48** 处，而按指令边界解析的 `call` 只有 **38** 条；10 处非 call 起点的 `E8` 全部落在既有指令内部）。

### 6.4 RIP 相对引用的解析

扫描 `48 8D 0D/05/15/35 XX XX XX XX`（`lea reg, [rip+disp32]`）与 `48 8B XX XX XX XX`（`mov reg, [rip+disp32]`），计算：

```
target = RIP + disp32      （RIP = 指令结束地址 = 指令起点 + 指令长度）
```

筛选落在目标区域的命中。样例如下（用于证明 `FF 25` 的目标）：

```
0x180055A70 + 6 = 0x180055A76
0x180055A76 + 0x16292 = 0x18006BD08
```

### 6.5 `E8 rel32` 闭集枚举

对某个具体目标（如某 thunk 的 VA），枚举全 `.text` 内所有 `E8 rel32` 且解析目标等于该 VA 的位置，得到一个**闭集**。闭集是「调用点在何处」类结论的唯一合格形式。

样例：

| 调用目标 | 全 `.text` 命中数 |
|---|---|
| `0x180055A70`（`hipLaunchKernel` thunk） | **60** |
| `0x180055960`（`__hipRegisterFunction` thunk） | **34** |
| `0x180001000`（W1 入口） | **0** |
| `0x180001EB0`（初始化包装体） | **2** |

「命中 0」同样是结论（例如 W1–W26 无外部直接调用者）。

### 6.6 `lea` → `call` 间距判据

在一处注册循环内，`lea rdx, [rip+X]`（取表槽位地址）与随后的 `call`（注册函数）之间的间距**恒为 `0x14`（20）字节**。这给出一个强判据：若某个 `call` 前 `0x14` 处存在 `lea rdx` 且其目标落在表指针区，则该 `call` 与表和该槽位配对。

该判据产生过一次实质更正：早期用「`call` 前 `0x40` 字节内」的宽窗口判定，得到「31 配对 + 3 不配对」；改用 `0x14` 固定间距后，**配对为 34/34，无不配对项**。三个此前被判为「不配对」的槽位（表 A 槽 30 / 31 / 32）各有独立注册站点。

### 6.7 模式扫描的能力边界

字节模式扫描**不能**：

- 判定「一条指令的语义」（需反汇编）；
- 判定「某内存位置在运行期被写入什么」（需运行期观测）；
- 排除「存在但形态不同」的结构（只能排除已列出的模式）。

因此模式扫描的全部「0 命中」结论，都必须在结论中写明检索模式清单与范围。

## 7. 交叉验证：独立重新推导

本项目方法论的**核心质量机制**是：**任何交付出去的数字，都必须由至少两条互相独立的路径得到**。

### 7.1 独立的含义

「独立」不是指「第二个人看了一眼」，而是指**实现独立**：

| 独立维度 | 做法 |
|---|---|
| **实现独立** | 核对方**不读取**任何既有 JSON / 中间产物，直接对 DLL 字节**自写解析器**重算 |
| **路径独立** | 同一指标用两条不同工具链取得（如哈希同时用 `Get-FileHash` 与 `hashlib.sha256`） |
| **坐标独立** | 同一数值从两条不同结构读取（如 LDS 需求同时从 msgpack 元数据与 device ELF 的 `.kd` 描述符读取） |
| **口径独立** | 同一结论用交换律形式再算一遍（如 `0x1000 + Σsize + Σgap == VirtualSize`） |

### 7.2 交叉验证的三种载体

**(a) 三条独立佐证（计数自洽）**

「34 个内核」这一结论由三条互相独立的计数佐证：

| 佐证 | 实测 | 与元数据的关系 |
|---|---|---|
| (a) 表 A `0x180056170..0x1800562A8` 内指向 `.text` 的代码入口 | **34** 项 | 相等 |
| (b) 全 `.text` 内对 `0x180055960`（`__hipRegisterFunction` thunk）的调用 | `call` → **34** 处、`jmp` → **0** 处 | 相等 |
| (c) 元数据内核条目数 | 272 ÷ 8 = **34** | 相等 |

三条佐证相互独立（PE 数据段指针表 / 代码调用点计数 / msgpack 条目数），结论一致。

**(b) 独立第二来源（同一数值两组结构）**

LDS 与私有段需求同时存在于两处：

1. msgpack 元数据（`.note` 节）的 `.group_segment_fixed_size` / `.private_segment_fixed_size`；
2. device ELF `.rodata` 内 64 字节 `.kd` 描述符的 `+0x00` / `+0x04` 字段。

实测对撞：**272/272 一致**，且 `entry == 代码符号 VA − .kd 符号 VA` **272/272、反例 0**。

**(c) 恒等式闭合**

结构解析若正确，则字节账目应当闭合到 0。已建立的恒等式包括：

| 恒等式 | 实测 |
|---|---|
| `0x1000 + Σsize(0x6514F0) + Σgap(0x4FB8) == 0x6574A8`（= 节 VirtualSize） | 成立 |
| 8/8 bundle `e_shoff + e_shnum × e_shentsize == size` | 差 0 |
| 权重容器：逐条走完终点 == `uint32@0x0C` | `5,673 == 5,673`，差 0 |
| 权重容器：`Σsize == 文件大小 − 载荷起点` | `147,683,778 == 147,689,451 − 5,673`，差 0 |
| 权重容器：`offset[0] == 0` 且 `offset[i] == Σsize[0..i-1]` | 153/153 成立，链违例 **0/153** |
| kernarg 组成：`kernarg == by_value + 66 + 190`（31 个内核） | 31/31 逐一成立 |

### 7.3 交叉验证抓到过的真实错误

独立重算不是形式主义，它抓到过若干实质性错误。典型类别：

| 类别 | 样例 |
|---|---|
| **编码宽度误记** | `k_reproject` 的 384 原按 uint32 给出编码串；改用 uint16 的 `CD 01 80` 后，原编码串在全文件 0 命中 |
| **口径混用** | 把「取值种数 8」当成「非零条目数 8」；正确为：`.sgpr_spill_count` 非零条目 **10**、`.vgpr_spill_count` 非零条目 **14**，取值种数（含 0）各为 8 |
| **端点截断** | 检索窗口上界截在表 A 槽 25，导致「全 `.text` 97 处」与自述范围不符；宽口径为 110 处 |
| **地址性质误标** | 三个地址（`0x1800124B0`、`0x1800120B0`、`0x180012EBC`）被多次标为函数入口，实测均落在既有函数中部 |
| **算术错误** | `descsz` 跨 bundle 最大最小差原记 1,410 B，实测去重 6 个取值，最大−最小 = **938** |
| **叙述与字节不符** | 「槽 30–32 无 `lea` 注册站点，值来自 `.rdata` 静态初值」被字节证据推翻 —— 三个槽位各有注册站点 |

### 7.4 冲突的处理

当两份材料对同一事实给出互斥结论时，处置规则：

1. **以字节裁定**，不以材料的新旧、详细程度或作者身份裁定；
2. 若两侧的字节引用**本身指向不同的地址**，则先确定地址的正确性，再比较内容；
3. 若两侧**都有缺陷**，则两者都不采用，按字节重写；
4. 裁定后，被推翻的表述**按其字节依据重写**，而不是简单删除。

## 8. 结果的可复现性

### 8.1 每条结论的三要素

本项目要求每条关键结论具备：

```
结论陈述
  ├─ 证据：原始字节串 / PE-ELF 字段 / 算术式
  ├─ 坐标：file / RVA / VA（三重）
  └─ 口径：该数值取自哪个统计口径
```

### 8.2 样本：一条完整结论的形态

以 `k_pre_block_1h_32_fp8` 的 LDS 需求为例：

| 项 | 值 |
|---|---|
| 结论 | 该内核的 `group_segment_fixed_size` = **64,640 B** |
| 证据 1（msgpack） | device `#1` 元数据内该内核 map 的 `.group_segment_fixed_size` 字段 |
| 证据 2（`.kd`） | `#1` bundle 的 `.rodata` @ `0xA180 + 64 × slot` 的 `+0x00` u32 字段读得 64,640 |
| 口径 | 该值在 272 条目口径下出现 **8 次**（8 目标各 1 条），**不得**写成「该内核 = 64,640」而不附口径 |
| 对撞 | 272/272 一致 |

### 8.3 已知的不可复现项

有若干结论的依据在**工作区之外**，本项目如实登记而不掩盖。例如：某份复核报告的「无未声明改动」结论，其依据是**内部自洽性核查**（修订记录编号连续、锚点存在、自述计数与实测对撞一致），而**未经首版对照验证** —— 因为首版实体在磁盘上 0 命中。凡引用此类结论，必须同时给出该限定语，**不得**升格为「经验证」。

## 9. 方法论的边界（诚实声明）

本章描述的方法**不能**做到以下事情。凡涉及以下类别的问题，本项目一律不给结论：

| 能力边界 | 原因 |
|---|---|
| **运行期行为**（某内核在什么条件下被调用、某全局量被写入什么值） | 无 AMD 硬件（E-1） |
| **指令级语义**（某段 device 代码具体做什么运算） | 无 AMDGPU 反汇编器（E-2）；34 个内核的 `.text` 合计 6,081,960 字节，**被反汇编的指令数 = 0** |
| **编译可行性**（重编后的内核能否编译、能否运行） | 无 Intel / SYCL 工具链（E-3） |
| **Xe / XMX 的具体能力**（SLM 上限、sub-group 宽度、XMX tile 约束） | 工作区内无任何 Xe 判据；DLL 内也不含任何 Intel / Xe / SPIR-V 目标 |

因此本项目的方法论产出的是**规格与评估**，其可信度来自**字节级可回溯性**与**独立重算**，而不来自运行验证。
