# 未解缺口与限制

本文集中说明**本项目无法回答的问题**，以及每个问题为什么无法回答。

列出这些内容的目的不是自我设限，而是让读者能够：
1. 判断哪些结论可以直接使用、哪些只能作为方向；
2. 避免重复已经走过的死路；
3. 知道要突破某个缺口，需要先补齐什么条件。

---

## 0. 三类限制

本项目遇到的限制可归为三类，性质完全不同：

| 类别 | 含义 | 突破条件 |
|---|---|---|
| **能力边界** | 在当前环境下**永久不可取得**的判据（如需要目标硬件、需要工具链） | 缺失的**物理条件**（硬件、工具链） |
| **未解项** | 在可得材料范围内**尚无判据**可以裁定 | 需要**新的证据来源**（上游源码、外部文档、运行期观测） |
| **外部依赖** | 判定依赖**工作区之外的规范或文档** | 查阅指定方向的外部资料 |

对每一类，本文都给出「为什么」与「需要什么」。

---

## 1. 能力边界（三条硬约束）

### 1.1 无 AMD 硬件 → 运行期观测路径不可用

**状态**：运行期观测路径**不可用**，且被确认为**永久条件**（不提供 AMD 硬件）。

**直接后果**：

- 不能在 AMD 上运行原版并观测其行为；
- 不能取得原版的输出（⇒ 数值对照类里程碑在**当前环境下不可达成**）；
- 不能通过运行期 dump 取得权重张量；
- 不能观测某个内核在什么条件下被调用（block 调度）；
- 不能观测某个全局量在运行期被写入什么值（`g_e4m3_lut` 的填充）。

**受影响的关键缺口**：§2 的「层 → kernel 绑定」直接因此封死。

### 1.2 无 AMDGPU 反汇编工具 → 指令级判据不可取得

**状态**：`llvm-objdump` 在工作区内检索命中 **0**；`capstone` 5.0.7 不支持 AMDGPU（模块内 AMD / GPU 相关属性检索命中 **0**）。

**量化后果**：

> 34 个内核的 `.text` 合计 **6,081,960 字节**（8 个 device ELF 之和），**被反汇编的指令数 = 0**。

**受影响的问题**：

- 不能判定某个 device 函数的**具体语义**（如 `swin_layer` 究竟做什么）；
- 不能判定 `g_e4m3_lut` 是否有 `.rodata` 之外的写点；
- 不能判定 `SwinLDS` / `BlobLayout` 两个类在 device 代码中的实际用法。

⇒ **只能做到「符号级」与「字节模式级」判断，不能做到「指令级」判断。**

### 1.3 无 Intel / SYCL 编译工具链 → 编译级判据不可取得

**状态**：`icx` / `icpx` / `dpcpp` / `clang` / `clang++` / `cl` / `hipcc` / `g++` 的 `Get-Command` **各命中 0**。

**直接后果**：

- 未能编译工作区内的任何 `.sycl` / `.hip` 源文件；
- **「移植版能否编译」在本环境内不可验证**；
- 工作区内的自研工程树（含 SYCL 尝试）**是否成功编译并运行过，无判据**：其 `build/` 内**无任何 `.sycl` 编译产物**。

### 1.4 三条约束的共同后果

> **本项目所有结论的验证上限是「静态字节级」。**

凡属运行期、指令级、编译级的判断，本文档集一律不给结论。

## 2. 核心缺口：「层 → kernel 绑定」不可取得

这是本项目**最重要、也最无法闭合**的缺口。

### 2.1 问题的形态

网络结构有 71 个 block（权重文件实测 `block0` … `block70`，**无缺号**），有 34 个内核。问题的形态是：

> **某个 block 的某一层，调用的是 34 个内核中的哪一个？**

**已确定的部分**：

| 项 | 状态 |
|---|---|
| **层数** | **已定**：权重实测 **1 层 × 47（block 0–22、39、48–70）/ 4 层 × 15（23–29、40–47）/ 5 层 × 9（30–38）** |
| **拓扑分段** | **已定**：`ENCODER_END = 22` / `BOTTLENECK_START = 23` / `BOTTLENECK_END = 47` / `DECODER_START = 48` |
| **34 个 kernel 名集合** | **已定**，且 kernel 名 ↔ wrapper 函数 ↔ 句柄表槽位 **34/34 静态闭合** |
| **「层 → kernel 绑定」** | **不可取得** |

### 2.2 四条路径全部封死

#### 路径 ①：DLL 静态分析 —— **已到边界**

所有可用的静态手段均已用尽，得到的**否定性结论**如下：

| # | 已确立的边界 | 实测 |
|---|---|---|
| 1 | dispatcher 函数体 `[0x180012380, 0x180012D26)` 内本签名比较（`cmp r32,0x1A`） | **命中 0**（体内的 `83 F8/F9/FA imm8` 仅 4 处，立即数 `0x10/0x10/0x20/-0x27`，无一处属 block 签名；最近的签名在 `0x180013117`，距 dispatcher 末端 `0x3F1`） |
| 2 | 按「1167 个 `.pdata` 函数体逐函数线性反汇编」口径的指令总数 | **82,170** 条（单次全 `.text` 线性反汇编仅 76,661 条，末条指令在 `0x180049EBE` 后遇非代码字节中断） |
| 3 | 该集合内立即数 `70` / `71` / `72` | 命中 **91** 处（`0x48` = 72 共 85、`0x46` = 70 共 4、`0x47` = 71 共 2），**无一处是 block 索引比较**（其中 55 处为 `sub` / `add rsp,0x48` 栈调整形态、36 处为非栈调整形态） |
| 4 | 「71 block」的来源 | **只有文档转述**；DLL 内无对应的立即数比较 |
| 5 | 派发点位置 | 只在 **4 处重编号函数内**，且**全在 dispatcher 之外** |
| 6 | dispatcher 38 处 `call` 目标 ∩ 14 个含 `hipLaunchKernel` 函数入口 | **= 0** |
| 7 | 重编号结果的存储 | 只写入 **BSS 型全局**（`0x180076394` / `0x180076398`，**无文件初值**）⇒ 静态只有写入点、**无初值表** |
| 8 | 3 个读点的形态 | 把值写入**只写不读**的栈帧字段后交给**虚调用**（虚表运行期填充） |
| 9 | 34 个包装体入口（31 个同模板实例 + 3 个辅助 wrapper） | **无 `E8` 直呼**（经句柄表间接调用） |
| 10 | 签名枚举的规模 | 同签名 **6 处**（4 处为 block 重编号内联副本，另 2 处 idx 949 / 951 **语义未判**） |

#### 路径 ②：工作区源码 —— **是空壳 + 与 DLL 不同构**

**空壳**：

- `OptiScalerIntegration.cpp` 的四个关键函数体（`EncodeInput` / `RunSwinBlock` / `RunProjectionBlock` / `DecodeOutput`）**全是 `return true;`**；
- 两个 `Get*Features()` 返回 `nullptr`；
- `NrBackend_Evaluate` 与 host 侧各阶段的函数体同样**均为 `return true;`**。

**不同构**：

| # | 依据 |
|---|---|
| 1 | **内核基名对撞 2/30**：该树去重基名 6 个；DLL 34 内核去重基名 **30** 个；**交集仅 2 个**（`k_swin_1h_32_fp8`、`k_swin_var`）⇒ **28/30 个 DLL 基名在该树中不存在** |
| 2 | **该树有而 DLL 无的 4 个基名**：`blend_output` / `dlssnr_imgenc` / `mlp_projection` / `residual_add` |
| 3 | **34 内核名在该树之外零命中**（全工作区 2,996 个非该树源文件中各 0 命中） |
| 4 | **Git 全历史亦无等价物**：历史源文件路径 5,951 个，路径子串 `engine/` **0**、`swin` **0**、`runtime_intel` **0** |
| 5 | **依赖的 SDK 不在工作区**：`hip/hip_runtime.h` 本体 **0 命中**；`rocm` 目录 **0**；`hipcc` **0** |

⇒ **该树是同网络的再实现工程，不是该 DLL 的源码**，其调度常量反映的是**该树作者的假设**，而非 DLL 的实际绑定。

**而且该树的调度规则已被数据推翻**：源码规则预测「瓶颈 23–47 统一 4 层」，权重实测为 **1 / 4 / 5 层混排**，**不一致块 = 10 个（30–39）**。

#### 路径 ③：权重文件 —— **已穷尽**

对 147,689,451 字节的权重文件做了**逐字节穷尽核查**：**140 个模式、覆盖含载荷区的全文件（100% 字节）、朴素串匹配（非正则、非近似、非抽样）**。

检索范围定义：

| 代号 | 字节区间 | 长度 |
|---|---|---|
| **H** | 索引区 `[0x0000, 0x1629)` | 5,673 B |
| **D** | 载荷区 `[0x1629, 0x8CD8FEB)` | 147,683,778 B |
| **W** | 全文件 | 147,689,451 B |

结果（全部 **0 命中**）：

| 类别 | 模式数 | 结果 |
|---|---|---|
| `shape` / `dims` / `dim` 类（含大小写变体、`rank`、`stride`） | 13 | **W 全 0** |
| `dtype` / 数值格式类 | — | **W 全 0** |
| **算子类型名**（`qkv` / `attn` / `conv` / `ffwd` / `swin` / `mlp` / `norm` 等） | **43** | **W 全 0** |
| **`kernel` 名集合**（10 个具名基名 + **超集前缀 `k_`** + `kernel` / `Kernel` / `KERNEL` / `__global__` / `__kernel` / `hipLaunchKernel`） | — | **W 全 0** |
| **独立 `block` 索引字段**（10 个字段名模式） | 10 | **W 全 0** |

**结构层面的三重证明**：

| # | 证明 | 证据 |
|---|---|---|
| **B1** | 容器内**只有 4 类字段**（`magic` / `count` / `indexEnd` / `entry[]`），`entry[]` 只有 **3 个子字段**（`name` / `offset` / `size`）。索引区 **5,673 B 逐字节 100% 归属这 4 类，未归属字节 = 0** | 逐字节记账 |
| **B2** | **不存在 `kernel` 名字段** | 上述检索 0 命中 |
| **B3** | **不存在独立 `block` 索引字段**：10 个字段名模式 0 命中；且**无承载字节** —— 若存在 `uint32 blockIdx`，索引区须 ≥ 6,285 B，**实测恰 5,673 B** | 字节记账 + 反证 |
| **B4** | **不存在算子类型字段**：43 个模式全文件 0 命中；名称中唯一的算子语义载体是后缀字面 `layer`（152 条）与 `blend_scale`（1 条），**粒度只到「第几层」不到「用哪个 kernel」** | 穷尽检索 |
| **B5** | **载荷内无隐藏元数据**：ASCII 可打印占比 **1.0273 %**；长度 ≥16 的 ASCII 串仅 **6 条**、最长 **21 B**（**短于最短名称长度 19 的完整长度级别上限 26**）；载荷区 ASCII 串与 153 条名称**交集 = ∅**；9 个步长自相关**无周期性峰值**；153 条载荷**覆盖间隙 0** | 全载荷区精确计数 |

**旁证（源码自证）**：两份树内解析器在需要 block 号时**都必须解析名字字符串**（`atoi(t.name.c_str() + 5)`）—— 这是「容器内确无独立 block 索引字段」的**反证**。

**排除「部分取得」的可能**：

| 档位 | 是否成立 | 排除理由 |
|---|---|---|
| **能** | 不成立 | 需容器内存在 kernel 名或映射表；B1 已证无承载字节、B2 已证 kernel 名字段 0 命中 |
| **部分** | **不成立** | 「部分取得」要求至少**能建立部分绑定**。实测 `entry.name` **只到 `block<N>.layer<L>.layer` 粒度**（152 条）+ `block70.layer0.blend_scale`（1 条），**不含任何 kernel / 算子标识**。B4 证算子名 43 模式 0 命中 ⇒ **连「该层属于哪类算子」都不在容器内，部分绑定亦无从建立** |
| **不能** | **成立** | B1–B5 五条独立证据同时指向同一结论 |

#### 路径 ④：运行期观测 —— **永久不可用**

原因见 §1.1。**这条路径不是「暂时不可用」，而是条件不存在**。

### 2.3 结论

> **「层 → kernel 绑定」在现有条件下不可取得。**
>
> 四条路径（DLL 静态分析、工作区源码、权重文件、运行期观测）**全部封死**。

**后果**：该缺口**直接卡住**路线图的 S5 阶段与其里程碑 M5-1。

**突破需要什么**（任一条）：

1. 具备 AMD 硬件，在 4 个读点 + **34 个句柄槽（表 A 29 + 表 B 5）**处做运行期记录，取得 `值 → kernel` 三元组；
2. 取得该 DLL 的**上游 pass 源码**（含 block 调度定义）；
3. 取得宿主侧 / `.hip_fat` 之外的 **block 维度定义**（该枚举上界在本 DLL 内未定）。

### 2.4 一处必须留意的相容性问题

**block 重编号**的输入含 `0x5A = 90`、输出含 `0x57 = 87`，**均 > 70**。

⇒ 与「block 索引空间为 0–70」的假设**不相容**；**该枚举上界在本 DLL 内未定**（已知 ≥ 90，重编号结果空间 ≥ 87）。

这意味即使在有了绑定之后，block 层的**输入 / 输出枚举**仍需先定界，否则分派表的定义域不确定。

## 3. 结构未解项

### 3.1 `VarParams` 168 B 的内部布局

**状态**：**现有条件下无解。**

**涉及内核**：k29、k30、k31、k32、k33（5 个 `k_swin_var`）。

**已确认的部分**：

| 项 | 值 |
|---|---|
| `by_value` 参数 `size` | **168** |
| `by_value` 参数 `offset` | **0** |
| `.kernarg_segment_size` | **424** |
| `.kernarg_segment_align` | **8** |
| 参数形态 | 1 个 `by_value`（168 B）+ 13 个 `hidden_*` |

**为什么无解**：

1. **`.args` 只声明 `by_value` 的总字节数，不含字段名 / 字段边界** —— 元数据在这一层是「黑盒长度」，不是结构体定义；
2. **工作区源码的结构体不能作为依据**：树内源码给出 16 个具名字段（7 个 `half*` + `int B,H,W,C` + `int windowSize,numHeads,headDim` + `float scale` + `int shiftSize`）；但**该结构按 64 位指针计 92 B，而 DLL 侧 `by_value` = 168 B ⇒ 两者不是同一布局**；且**该树与 DLL 不同构**（28/30 去重基名不在其中）；
3. **外部材料不在工作区内**（上游 pass 源码、网络定义）。

**后果**：5 个 `k_swin_var` 的 kernarg 打包**无法逐字段重建**；Xe 侧的参数打包要求也因此无法确定（外部待查项 G-17）。

**同族未解**：§3.2 的 `SwinParams` 40 B。

### 3.2 `SwinParams` 40 B 的内部构成

**状态**：**现有条件下无解。**

**涉及内核**：k0（`k_swin_1h_32_fp8`）。

**已确认的部分**：

| 项 | 值 |
|---|---|
| `by_value` 参数 `size` | **40** |
| `by_value` 参数 `offset` | **0** |
| `.kernarg_segment_size` | **296** |
| `.kernarg_segment_align` | **8** |
| 参数形态 | **1 个 `by_value`（40 B）+ 13 个 `hidden_*`，且无任何 `global_buffer` 参数** |

**为什么无解**：

1. **40 B 内装哪些字段、各几字节：无解** —— 判据边界同 §3.1（`.args` 只声明总字节数）；
2. **与源码 `SwinParams`（按 64 位指针计 92 B）的差值 52 B 的成因：无解**；
3. 外部材料（上游 pass 源码、网络定义）不在工作区内。

**一处需要说明的撤回**：「`SwinParams` 的 40 B 已解释（指针走 `global_buffer`）」这一说法**是错的** —— k0 的 14 个 `.args` 中**没有任何 `global_buffer` 参数**（全库仅 24 个 `global_buffer` 参数，全部属于 k26 / k27 / k28 三个例外内核）。该说法已被撤回。

### 3.3 权重尾部 190 B 与 16 B 空洞的字段归属

**状态**：**未解出。**

**已确认的部分**：

- **16 B 空洞**：位于隐藏区 `+0x18`–`+0x28`（`hidden_remainder_z` 末端与 `hidden_global_offset_x` 起点之间），**31 内核 × 8 目标恒定**，无对应 `.args` 条目；
- **190 B 尾部**：差值 `+190` 出现 **248** 次（31 内核 × 8 目标），差值 `+0` 出现 **24** 次（3 内核 × 8 目标）；两处均**无对应 `.args` 条目**。

**为什么无解**：

- 元数据不含字段名 / 边界；
- 需要指令级反汇编（E-2 不可用）或上游源码。

**顺带未解**：`190 mod 8 = 6`，**与 `.kernarg_segment_align = 8` 的关系未解**。

**后果**：无法判断这两段在 Xe 侧是否需要对齐（外部待查项 G-41 / K6）。

### 3.4 `.data` 17 项指针表的运行期填充机制

**状态**：**能力具备；实际填充路径未证。**

**已证的部分**：

- 17 槽位于 `0x180076440..0x1800764C0`，**超出 `.data` 的 raw 覆盖范围**（`.data` 文件映像只到 VA `0x180076200`）；
- **无文件字节**；
- **无 `.reloc` 覆盖**（`DIR64` 计数 0）；
- 该模块**具备** `GetProcAddress`（直接 IAT 引用 **25** 处）、`LoadLibraryA`、`LoadLibraryExW`、`FreeLibrary`（**7** 处）、`GetModuleHandleA/W`（**9** 处）的**运行期解析能力**。

**未证的部分**：实际由**哪个调用点、用哪个 API** 回填这 17 个槽。

**为什么未证**：需要运行期观测（E-1 不可用）；静态层面只能证明「有能力」，不能证明「实际用了」。

### 3.5 `swin_layer` 的语义与出现范围成因

**状态**：**未判。**

**已确认的部分**：

| 项 | 值 |
|---|---|
| 符号名 | `_Z10swin_layerR7SwinLDSPKhRK10BlobLayouti`（**非模板**；`7` 是名字长度前缀） |
| 出现范围 | **`#2` gfx11-generic / `#3` gfx1100 / `#4` gfx1101 / `#5` gfx1102**；`#1` / `#6` / `#7` / `#8` 命中 **0** |
| 大小 | `st_size` = 135,092（`#2`、`#5`）/ 135,096（`#3`、`#4`）；VA 均 `0xBD00` |
| 是否在 34 个 kernel 名之内 | **否** |
| 是否有 `.kd` 描述符 | **无** |
| `.symtab` 条目数 | `#2`–`#5` = 348；其余 = 347；**`#1` 与 `#2` 的符号集合差集恰为该符号一个元素**；8 个 bundle 符号并集 = 348、共有 = 347 |
| 工作区源码中的对应物 | `SwinLDS` / `BlobLayout` 在该工程树全树 **命中 0** ⇒ **无源码可参照** |

**为什么未判**：

1. 与 34 个 kernel 的**调用关系未取证**（无 AMDGPU 反汇编器，E-2）；
2. 其存在范围为何只在 4 个目标（而非 8 个）**成因未解**。

**能支撑的结论边界（必须严格遵守）**：`swin_layer` 符号**只能支撑**「该 device ELF 内**存在一个以 `SwinLDS` 类为第一形参的设备函数**」这一层。它**不能**支撑：

- 「该函数的 LDS 用量」；
- 「该函数与 34 个 kernel 的调用关系」；
- 「该函数在 Xe 侧如何改写」。

⇒ 由此派生的 **LDS 重划一级判据当前未落地**（外部待查项 G-20 / G-21）。

### 3.6 `g_e4m3_lut`（512 B 全零）的语义

**状态**：**未判。**

**已确认的部分**：

| 项 | 值 |
|---|---|
| 位置与大小 | 8 个 device ELF 的 `.rodata` 内均有一个 **512 B** 的 `g_e4m3_lut` 对象 |
| 字节 | **8 目标全部 512/512 字节为 `0x00`** |
| `.kd` 引用 | 272 个描述符内**无任何字段等于该符号 VA** |
| 全 DLL 引用点 | **每 bundle 2 处 8 字节编码**（`.rodata` 内 1 处 + `.text` 内 1 处） |
| 名称含义 | 含 `e4m3`（FP8 的一种格式）与 `lut`（查表） |

**为什么未判**：

- 判定「是全零占位还是运行期填充」需要**写点判定**，后者需要指令级反汇编（E-2 不可用）；
- 或需要**运行期内存镜像比对**（E-1 不可用）。

⇒ 两条路径同时不可用，故该问题在本环境内**不可裁定**（外部待查项 G-22）。

### 3.7 `k_expand` / `k_contract` 的算子语义

**状态**：**未解。**

**问题的形态**：两个名称（Expand / Contract）在张量算子语境下**可指向多种语义**（广播 / 张量收缩 / 索引展开）。

**可用判据只有**：名称与 `B` 尺寸（分别 24 B / 48 B）。

**判据不足以在多种语义间选择**；且工作区工程树侧**亦无对应实现**（两名字在该树各 **0 命中**）。

⇒ 需先取得算子语义，才能判定 Xe 侧对应原语（外部待查项 G-19）。

### 3.8 两个唯一极值的成因

**状态**：**未解。**

| 内核 | `private_segment_fixed_size` | 出现范围 |

### 3.9 `k_ffwd` 系列 `group` 跨目标取 0 与 24,576 的成因

**状态**：**未解。**

## 4. `71 block` 的枚举语义

### 4.1 问题的形态

「71」这一数字在两个来源中出现：

| 来源 | 形态 |
|---|---|
| **权重文件** | 条目名覆盖 `block0` … `block70` 共 **71 个 block、无缺号** —— 这是**实测** |
| **工作区源码** | `constexpr uint32_t NUM_BLOCKS = 71;` —— 这是**声明** |

但「71」在 **DLL 的静态字节中**：

| 检索 | 范围 | 结果 |
|---|---|---|
| 立即数 `70` / `71` / `72` | 「1167 个 `.pdata` 函数体逐函数线性反汇编」口径的 **82,170** 条指令 | 命中 **91** 处（`0x48` = 72 共 85、`0x46` = 70 共 4、`0x47` = 71 共 2），**无一处是 block 索引比较** |
| 本签名比较（`cmp r32,0x1A`） | dispatcher 函数体 | **命中 0** |

⇒ **「71 block」在 DLL 内只有文档转述，没有对应的立即数比较。**

### 4.2 block 重编号（已定案的部分）

`.text` 内有 **4 处**同签名（`cmp r32,0x1A`）**重编号**内联副本（另 2 处 idx 949 / 951 语义未判）：

| 输入 | 输出 |
|---|---|
| `9` | `0x0A`（10） |
| `0x17`（23） | `0x18`（24） |
| `0x1B`（27） | `0x1C`（28） |
| `0x5A`（90） | `0x57`（87） |
| 其余值（**含 `0x1A` = 26**） | **保持原值** |

四处的分支顺序两两不同（位置 1 / 2 先判 `0x5A` 后判 `0x1B`；位置 3 / 4 先判 `0x1B` 后判 `0x5A`），但分支语义完全一致，属**同一函数被内联四次**。

⇒ 因此早期表述「已确定的 block 值只有 5 个：9、23、26、27、90」在语义上须改写为：

> **`26` 只是 `jg` 的比较界、不被重编号；真正被特判重编号的是 9 / 23 / 27 / 90 四个。**

### 4.3 未判的部分

| 项 | 状态 |
|---|---|
| **4 处重编号的场合**（在什么条件下调用） | **未判** —— 需运行期观测 |
| **重编号结果的用途** | **未判** —— 结果只写入 BSS 型全局（无文件初值）；3 个读点把值写入**只写不读**的栈帧字段后交给**虚调用**（虚表运行期填充） |
| **同签名另 2 处（idx 949 / 951）的语义** | **未判**。坐标：`0x180048A44`（idx 949，原始字节 `83 F9 1A 74`）、`0x180048ECC`（idx 951，原始字节 `83 FA 1A 0F`）。本项目**不主张**其为重编号副本 |
| **block 枚举的上界** | **未定** —— 输入含 `0x5A = 90`、输出含 `0x57 = 87`，均 > 70 |

### 4.4 相容性裁决

| 项 | 内容 |
|---|---|
| 冲突 | 输入 `0x5A = 90`、输出 `0x57 = 87` **均 > 70**，与「block 索引空间 0–70」**不相容** |
| 状态 | **该枚举上界未定**；本项目**不给结论** |
| 影响 | block 层的**输入 / 输出枚举**在移植时需先定界，否则分派表的定义域不确定 |

## 6. 结论的强度说明

### 6.1 三条必须随引用给出的限定

1. **跨目标一致性结论仅覆盖参数面**：`.kernarg_segment_size`、`.args` 元素数、逐参数 `.offset` / `.size` / `.value_kind` 在 8 目标一致（238/238 判定格、`args` 字节 SHA256 272/272）；**资源类字段另有差异**（16 个字段实体中 8 个不一致）。

2. **算子语义只能到「名称推定」**：四条否证同时成立（源码路径判死 + 对照模块不成立 + 无硬件 + DLL 内算子名 0 命中）。⇒ 该结论**不构成算子语义的验证结论**。

3. **「已有实现」不构成能力证明**：工程树覆盖 **6/34** 内核，其唯一 `joint_matrix` 用法集中在 **1 个 0 实例化的模板**内，其余实现体是**标量循环**；且其共享内存用量与寄存器压力**未取得判据**。

### 6.2 口径混用会产生错误结论的七处

| # | 口径 A | 口径 B | 后果 |
|---|---|---|---|
| 1 | **272 条目口径** | **34 内核口径** | `.max_flat_workgroup_size` = 256 × 208 / 1024 × 64 vs 256 × 26 / 1024 × 8 |
| 2 | **口径 1（字段 × 内核对）163** | **口径 2（与 `#1` 比格数）605** | 按「163 × 7」估得 1141、按「163 × 28」估得 4564，**两个都是错的** |

### 6.4 一处能力边界登记

> **登记目的**：防止把「未发现未声明改动」误读为「已验证无未声明改动」。

某份复核报告的**首版对照在本环境内不可执行**：独立核查确认**首版实体在磁盘上 0 命中**（按 `73,194 B` 检索 **0 个**；按哈希 `3A03DE7A` 检索**仅命中该复核报告自身**，因它引用了该常量字符串 —— **无任何文件的实际哈希等于 `3A03DE7A…`**；按文件名检索**仅**现行版一处，**无 `.bak` / 旧版副本 / 同级备份**）。

⇒ 引用该复核的「**无未声明改动**」结论时，其依据是**内部自洽性核查**（修订记录编号连续、锚点存在、自述计数与实测对撞一致），**未经首版对照验证**。凡出现此类表述，**必须**同时给出该限定语，**不得**升格为「经验证」。

## 8. 给下游读者的三条建议

1. **凡引用数值，先看口径**。§6.2 列出的七处口径混用会产生错误结论；本文档集在每一处需要口径标注的地方都给出了显式标注，请一并沿用。

2. **凡引用「需外部资料」的项，不要把它写成「已具备条件」**。本项目在路线图阶段划分中已经把每一阶段的**前置未闭合项**显式列出；S0 阶段就是为闭合这些前置项而存在的。

3. **凡涉及运行期、指令级、编译级的判断，本项目一律不给结论**。这不代表这些判断不重要，而是代表**它们需要本项目不具备的条件**。若读者具备这些条件（AMD 硬件、AMDGPU 反汇编器、Intel 工具链），本文档集给出的**坐标、计数、恒等式与检索模式**可以直接用于复算与推进。
